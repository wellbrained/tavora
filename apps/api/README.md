# @tavora/api

Tavora's online game database: a small read-only service that answers game searches from its own dataset. The app asks it; it never calls Wikidata or Steam while running. The only user data it holds is accounts (an email address and its sign-ins), and only once it can send email. Besides that it keeps plain daily totals (see Counting below), which say nothing about anyone.

Needs Node 22.18 or newer (it runs the TypeScript directly and uses `node:sqlite`).

## Run it

```sh
pnpm --filter @tavora/api dataset      # build data/games.sqlite (see below)
pnpm --filter @tavora/api dev          # http://127.0.0.1:4010, restarts on changes
```

| Variable | Default | Meaning |

## API

- `GET /v1/games/search?q=<text>&limit=<1-20>` returns `{ "results": [{ "id": "elden-ring", "name": "Elden Ring", "steamAppId": 1245620 }] }` (`steamAppId` is `null` for games without one; the app uses it to fetch the game's icon from Steam itself), best match first: exact name, exact alias, name prefix, alias prefix, then every word as a word start. Case, accents and apostrophes are ignored. `q` is at most 100 characters, `limit` defaults to 8.
- `GET /v1/health` returns `{ ok, games, builtAt }`.
- `POST /v1/steam/library` with JSON `{ "profile": "<steamcommunity.com profile link or SteamID64>" }` returns `{ "games": [{ "appid": 1245620, "name": "ELDEN RING", "id": "elden-ring" }] }`, sorted by name; `id` is the canonical id when the dataset knows that Steam appid, otherwise `null`. The service asks Steam's Web API with its own key, passes the list straight back and stores nothing. 400 for a profile it cannot read, 404 for an unknown custom name, 502 when Steam fails or the profile's Game details are private, 503 without a key, 415 unless the body is JSON. 6 requests a minute per client. It is a POST so the profile is in no URL.
- `GET /v1/icons` returns `{ "notice": "…", "takedown": "<contact>", "icons": [{ "id": "diablo-iv", "names": ["Diablo IV", "Diablo 4"], "sha256": "…", "size": 9527 }] }` and `GET /v1/icons/<id>.png` the icon itself (a PNG of at most 256 px). 503 and 404 while `TAKEDOWN_CONTACT` is not set. The app downloads the list, matches it on the user's PC and asks only for the icons it needs, so the service sees which icons are asked for, one request each, and nothing else (no log is kept). These two are the only answers that may be cached (5 minutes for the list, a day for a file).
- `POST /v1/icons/submit` with `Authorization: Bearer <token>` (a signed-in account) and JSON `{ "id": "diablo-iv", "name": "Diablo IV", "source": "installed", "icon": "<base64 PNG or .ico>" }` offers an icon the user's PC has and the service lacks. The id must be a game in the dataset that has no icon yet, or a `local-` id for a game the user added by name: then `name` decides. A name the dataset knows for exactly one game is offered for that game; a name no game has is offered as a custom game, listed under `local-<slug of the name>` and matched by that name only; a name several games share is refused. The file must be a PNG or an .ico of 32 to 256 px and at most 200 KB. It is cleaned (a PNG keeps only the chunks that make the picture), queued and answered `202 { "status": "received" }`, the same for a new offer, a repeat, a blocked file and a blocked account. Nothing is served until a person approves it. The account that sent an offer is kept with it until it is approved or denied, and an account whose offer was blocked is refused from then on. `400` for what is not an icon offer, `401 signed-out` without a valid sign-in, `409` when the game already has an icon, `413` over 400 KB, `415` unless the body is JSON, `429` with 100 offers from the account already waiting, `503` while `TAKEDOWN_CONTACT` is not set, without accounts, or while the queue is full. 100 offers an hour per client.
- **Accounts** (`/v1/account`). An account is an email address; the user signs in with a 6-digit code sent to it, never a password. JSON bodies only; errors are `{ error, reason }`, and the app translates `reason` (`bad-email`, `bad-request`, `wrong-code`, `too-many`, `daily-limit`, `mail-failed`, `signed-out`, `same-email`, `email-taken`, `not-found`, `unavailable`). All of it answers `503` while the service cannot send email.
  - `POST /code { email, language }` mails a code (`language` is `en` or `de`) and answers `202 { "status": "sent" }`, the same whether or not the address has an account. A code lasts 10 minutes, a new one replaces the last, 5 wrong tries spend it; one address gets at most 3 codes in 15 minutes and 10 a day (all purposes together), and a client may ask 10 times an hour.
  - `POST /verify { email, code, os, create }` signs in. For an address with an account it answers `{ status: "signed-in", token, device, account }`. For a new address it answers `{ status: "no-account" }` and keeps the code, so the app can ask the user; the same call with `create: true` makes the account (`status: "created"`). `os` is `windows`, `linux`, `macos` or anything else (kept as `other`). A client may check 20 codes in 15 minutes.
  - Signed in, with `Authorization: Bearer <token>`: `GET /` returns `{ account: { email, createdAt }, devices: [{ id, os, name, createdAt, lastUsedAt, current }] }`; `POST /sign-out` ends this sign-in; `PUT /devices/<id>/name { name }` renames one (at most 40 characters; a sign-in may send its `name` too); `DELETE /devices/<id>` ends another; `POST /email/code { email, language }` and then `POST /email { email, code, language }` change the address (the code goes to the new one, a notice to the old one, and `409 email-taken` comes only after the right code); `POST /delete/code { language }` and then `POST /delete { code }` delete the account and every sign-in at once. A token unused for a year stops working. `GET /profile` returns `{ profile: { name, initials, picture, updatedAt } | null }` and `PUT /profile` with the same fields keeps it unless the account already has a newer one (`updatedAt`, never later than now), answering with what the account has; `picture` is a base64 PNG of 256 px and at most 512 KB, or `null`; the name is at most 32 characters, the initials 3. The profile is only ever shown to its owner.
  - **Discord login** (decided 2026-10-16), a second sign-in method; an account has an email, a Discord login or both, never none. The app runs Discord's browser sign-in itself (PKCE, scope `identify`, back to `http://127.0.0.1:53682/discord`) and sends `{ code, verifier }`; the service exchanges them with Discord (public client, no secret), reads the user id and username, revokes the token and keeps neither it nor anything else. `POST /discord/sign-in { code, verifier, os }` signs a known login in (refreshing its username) or answers `{ status: "no-account", ticket, discord: { name } }`, holding the checked login for 10 minutes; `POST /discord/create { ticket, os }` then makes a Discord-only account. Signed in: `POST /discord { code, verifier }` connects Discord (`409 discord-taken` when another account has it: never merged, never linked by email), `DELETE /discord` and `DELETE /email` remove a method (`409 last-method` for the last one), `POST /delete/discord { code, verifier }` deletes an account by a fresh sign-in with its own Discord login (`/delete/code` answers `409 no-email` without an address). Answers show `discord: { name } | null`, never the Discord id. Errors also `discord-refused` (400), `discord-unreachable` (502), `discord-expired`, `discord-mismatch`.
  - **Module developer**, signed in: `GET /developer` returns `{ developer: { name, changedAt, nextChangeAt } | null, keys: [{ fingerprint, linkedAt }], publishTokens: [{ id, name, createdAt, expiresAt, lastUsedAt }], requests: [{ old, new, leaked, requestedAt, status }] }` (`status` is `waiting`, `done` once the served signed lists hold it, or `declined`); `PUT /developer { name }` sets the public developer name (3 to 32 letters, digits, spaces, dots, dashes or underscores; unique when case and those separators are ignored; never one containing "tavora" or a reserved word; it changes once in 30 days, and a name given up stays blocked for other accounts for 30 days; errors `bad-name`, `name-taken`, `name-reserved`, `name-too-soon` with `nextChangeAt`); `POST /keys/code` gives a one-time code `{ code, expiresAt }` (8 characters, 10 minutes, a new one replaces the last; `409 no-developer-name` without a name); `POST /keys/<fingerprint>/replace { new, leaked, language }` asks to replace a lost (or leaked) linked key with another key linked to the same account, for the maintainer to sign offline from the review page, and emails the account's address (`404 not-found` unless both are linked here, `409 key-in-request` while another replacement for it waits); `DELETE /keys/<fingerprint>` unlinks a key (`409 key-in-request` while it is part of a waiting replacement). `POST /publish-tokens { name }` makes a publish token for CI (name 1 to 40 characters; at most 10 per account; good for a year) and answers `201 { token, ...developer }`, the only time the token is shown (the service keeps its hash); errors `bad-name`, `no-developer-name`, `too-many-tokens`. `DELETE /publish-tokens/<id>` removes one. Module id prefixes, claimed before the first publish (a prefix follows the rule for a module id's first part: lowercase letters and digits, starting with a letter): `GET /prefixes` returns `{ prefixes: [{ prefix, claimedAt, published }], max }` (`claimedAt` in milliseconds, by a claim or the first publish; `published` when any module, listed or not, has an id under it); `GET /prefixes/<prefix>` returns `{ prefix, state }` with `state` one of `held`, `free`, `taken`, `reserved`, `too-many` or `invalid`; `POST /prefixes/<prefix>` (a JSON body, `{}`) claims it and answers `{ prefix, state: "held" }`, also when the account held it already, or `403` with `reason` `prefix-taken`, `prefix-reserved` or `too-many-prefixes`, or `400 invalid`. Claims count toward the 3 prefixes an account holds, and a publish token may publish a first version under a claimed one. 30 claims an hour per client, then `429 too-many`.
  - Kept: the address, when the account was made, the profile (name, initials, picture, when it changed), a Discord login's user id and username, the developer name and when it changed, the public halves of linked publisher keys, and per sign-in a hash of its token, the operating system and two dates. Codes and the per-address counters are kept under a hash of the address and are gone within a day. No connection address and no PC name is stored.
  - **Cloud copy** (decided 2026-10-19), signed in, under `/v1/account/copy`: one copy of the user's Tavora data per account, which only the user can read. The app encrypts everything on the PC before it leaves, with a key the service never sees; the service holds opaque **parts** (each named by a 32-byte id the app derives with that key, so equal content is stored once and no id says which file it is) and an encrypted **manifest** saying which parts make the copy. Bodies are `application/octet-stream` (415 otherwise), so a web page cannot send one without a preflight. `GET /` returns `{ copy: { version, size, updatedAt } | null, limit }`; `GET /manifest` the manifest's bytes with `X-Copy-Version` (`404 no-copy`); `POST /parts` stores parts, one after another as a 32-byte id, a 4-byte big-endian length and the bytes (a part at most 4 MB plus 1 KB, about 8 MB per upload), answering `{ stored }`; `POST /parts/get` with ids one after another (at most 2048) answers the parts it has in the same framing, in the order asked, about 8 MB at most and always at least one; `PUT /` with the version it started from and the part count (4 bytes each, big-endian), the part ids and then the manifest makes a new version and answers `{ version, size }`, or `409 copy-changed` with the current `version` when another PC saved one first, `409 missing-parts` with how many, or `413 copy-full`; `DELETE /` removes the copy at once; a new copy's versions go on from the deleted one's, so a PC that missed the delete can't write over it. A copy is at most 100 MB (the manifest and the parts it uses); while a new version uploads, the parts kept may reach 200 MB, then `413 copy-full`. Parts no version uses are dropped when a new version is saved. Deleting the account deletes the copy. 300 requests a minute per client. Kept: the parts, the manifest, the version, its size and when it changed, in `copies.sqlite`, which the daily backup leaves out (after a loss the PCs upload again). `503 unavailable` without accounts.
  - **Key vault** (decided 2026-10-20), signed in, under `/v1/account/vault`: one small sealed blob per account, opened only by the user's recovery key (the same key as the cloud copy, under its own derived key). Its being there tells a new PC that the account already has a recovery key. `GET /` returns its bytes with `X-Vault-Version` (`404 no-vault`); `PUT /` with the version it started from (4 bytes, big-endian) and the sealed bytes (at most 64 KB) answers `{ version }`, or `409 vault-changed` with the current `version`; `DELETE /` removes it. Bodies are `application/octet-stream` (415 otherwise). Kept in the accounts database, so the daily backup has it; deleting the account deletes it. 60 requests a minute per client.
  - **Suspended accounts** (decided 2026-10-26): the maintainer can suspend an account from Tavora Admin. Its sign-ins are gone, `POST /verify` (after a right code), `POST /discord/sign-in` and `POST /discord/create` answer `403 { reason: "suspended" }` without creating a sign-in, and publishing answers `403 { reason: "suspended" }`. A suspended person can still delete the account: `POST /delete/suspended/code { email }` (always `202`, a code is mailed only for a suspended account), `POST /delete/suspended { email, code }` (`204`, else `400 wrong-code`) and `POST /delete/suspended/discord { code, verifier }` (a fresh Discord sign-in; `204`, else `400 discord-mismatch`) delete it without making a sign-in. The app shows "Your account is suspended." Kept in `suspensions` in `accounts.sqlite` (reason, note, date, last use).
- **Publishers** (`/v1/publishers`), there while accounts are. `GET /<fingerprint>` returns `{ name }`, the developer name of the account a publisher key is linked to (`404 unknown` otherwise; cached publicly for an hour), and nothing else about the account. `POST /link { code, publicKey, signature }` links a key: `publicKey` is the raw 32-byte Ed25519 key in base64 and `signature` its signature over `tavora-key-link-1\n<code>`, which `tavora-pack link` makes; the signature is checked before the code is used up, so only whoever holds the key can link it. Answers `{ status: "linked", fingerprint, name }`; errors `bad-signature`, `wrong-code`, `key-taken` (another account's key), `too-many-keys` (20 per account). Link attempts count with code checks: 20 in 15 minutes per client.
- **Module catalog** (`/v1/catalog`), read-only, no sign-in (Milestone E; the threat model is `docs/catalog-threat-model.md` in the vault). Community modules only; Tavora's own stay bundled with the app. An entry is a module at its newest version: `{ id, name, description, version, minTavora, games, personalWorkspaces, permissions: { network, connectors }, owner, publisher, zip: { sha256, size }, publishedAt, notes }` (plus `workspaces`, the old name of `personalWorkspaces`, for Tavora 0.21.42 and older). `owner` is the publisher key's fingerprint; `publisher` is the developer name of the account that key is linked to, or `null`, never a name the module claims. `notes` are that version's lines from the module's changelog, plain text.
  - `GET /v1/catalog` returns `{ modules: [entry] }`, every listed module; `?game=<id>` only those for that game and for any game; `?personal=1` only those a personal workspace offers (`?workspace=1` for Tavora 0.21.42 and older). The app takes a whole index and decides on the PC what to update, so it never sends what a user has installed. Cached publicly for 5 minutes.
  - `GET /v1/catalog/modules/<id>` returns `{ module: entry, versions: [{ version, publishedAt, notes }] }`, newest first.
  - `GET /v1/catalog/zips/<sha256>.zip` returns a listed module's zip, named by its hash and cached for a year. The app checks the hash and then installs it exactly like Install from zip; the service is never what makes a zip trusted.
  - `GET /v1/catalog/waiting` (same `Authorization: Bearer` as publishing) lists the account's own versions waiting for review with their reasons, and `DELETE /v1/catalog/waiting/<sha256>` withdraws one (its row, zip and pictures go; `404 not-waiting` for anyone else's or a listed one). `tavora-pack withdraw <zip | sha256>` calls it with a publish token.
  - `POST /v1/catalog/publish` with the zip as `application/zip` (at most 50 MB) and `X-Tavora-Signature`: the publisher key's Ed25519 signature (base64) over `tavora-catalog-publish-1`, a newline and the zip's SHA-256 in hex. `tavora-pack publish` sends it, with `Authorization: Bearer` and either the account's sign-in (Tavora uploads for `tavora-pack`) or a publish token (`tvp_…`, from CI). The key alone publishes nothing: the key that signed the zip must be linked to an account, the upload signature must be that key's, so a zip shared by hand cannot be published by whoever got it, and the sign-in or token must be that same account's. A token can't claim a new prefix, but publishes under one the account claimed. Every upload sends the account's address an email (in the `Accept-Language` language) naming the module, the key, and Tavora or the token's name. The account must hold the id's prefix (the part before the first dot), which it gets by claiming it (above) or the first time it publishes under a free one: at most 3 per account, and none that a developer name could not be (`tavora`, `official`, `local` and the other reserved words). Only a module's 3 newest versions keep their zip: a new version deletes the zips of older ones for good (their rows, notes and hashes stay, the zips are no longer served), and what it deletes is counted as free when the upload is checked against the account's and the catalog's room. The zip is checked like a hand-added one, then runs the automatic checks of [Review before listing](#review-before-listing): when all pass it is listed at once, otherwise it waits for a person. Answers `201 { status: "published", id, version, sha256 }` (listed), `202 { status: "waiting", id, version, sha256, reasons: [{ check, text }] }` (uploaded, not listed, the developer and `MAINTAINER_EMAIL` are emailed; `tavora-pack publish` prints Waiting for review), or `{ error, reason }` with `reason` one of `invalid` (400, `error` says why), `sign-in-needed` (401: no sign-in or token, or one that doesn't work), `wrong-account`, `token-new-prefix`, `key-not-linked`, `bad-signature`, `prefix-taken`, `prefix-reserved`, `too-many-prefixes` (403), `key-revoked` (403: the signed revocation list revokes the key), `key-leaked` (403: the key's account reported it as leaked and the request wasn't turned down), `conflict` (409: an older or same version, or the id belongs to another key), `daily-limit` (429: 10 versions an account in 24 hours), `account-full` (413: 200 MB of stored zips an account), `too-big` (413), `catalog-full` (507: the review page shows since when, and `MAINTAINER_EMAIL` gets an email at most once a day, until an upload fits again), `banned` (403: the account or one of its keys was banned), `declined` (403: this exact zip was declined), `too-many-waiting` (429: an account may have 5 versions waiting), `too-many` (429: 30 uploads an hour per client; none of these four for the account with `MAINTAINER_EMAIL`) or `unavailable` (503, without accounts). A module's versions come from the key of its first version, or from a key that succeeds it by the signed successions list in the same account (the succession's `account` is the account id in `accounts.sqlite`); the listing's `owner` is the key that signed its newest zip, which the app checks the zip against. The service checks the stored revocation and succession lists against Tavora's catalogue public key itself, so a list put on the server without the catalogue key changes nothing. Prefixes stay held when an account is deleted, so nobody can publish new modules under its name; the maintainer can release one by hand.
  - `POST /v1/catalog/report { id, owner, sha256 }` (JSON, exactly these three fields, at most 500 bytes) records that a user pressed Report on a listed zip: the module id, its key's fingerprint and the zip's hash, and nothing about the user. Reports hide nothing; they wait on the review page, where a person decides. The publisher gets an email at most once a day when their key's account has an address, and only while more than the emails kept for sign-in codes are left that day. Answers `202 { status: "received" }`, `404` for a zip the catalog does not list under that id and key, `400`, `415`, `429` (10 reports an hour per client) or `503`.
  - **Ratings and reviews** (decided 2026-10-21), there while accounts are (`503 unavailable` otherwise). A listing's `rating` is `{ average, count, stars: [1★, 2★, 3★, 4★, 5★] }` over every version, or `null`; the app says "New" below 3 ratings. `GET /v1/catalog/modules/<id>/reviews` returns `{ summary, reviews: [{ id, stars, text, version, createdAt, updatedAt, author: { name, initials, picture: { sha256, size } | null }, reply: { text, updatedAt } | null }] }`, the 100 newest with text that aren't hidden (cached for a minute); `author` is the reviewer's profile, which shows only here, and a name the word filter refuses is `null`. `GET /v1/catalog/reviews/<id>/picture/<sha256>.png` is that picture, only while the review shows. Signed in: `GET /v1/catalog/modules/<id>/review` returns `{ review, own }` (`own`: the account holds the id's prefix or the module's key, so it can't rate); `PUT` with exactly `{ stars: 1-5, text: at most 500 characters or null, version: a published version }` rates (one rating per account and module, replaced by the next); `DELETE` removes it. The module's publisher puts one reply under a review with text, `PUT /v1/catalog/reviews/<id>/reply { text }`, or takes it back with `DELETE`. `POST /v1/catalog/reviews/<id>/report` (no body) reports a shown review, with nothing about who sent it; it waits on the review page's Reviews tab, where Hide takes its text and reply off and keeps its stars. A word filter (`review-filter.ts`) refuses texts with slurs (`400 review-words`) or links and email addresses (`400 review-link`). Errors `own-module`, `not-publisher` (403), `signed-out` (401), `bad-request`, `too-many` (429: 30 writes an hour per client). Kept: per rating the account id, module id, stars, text, version and two dates; per reply its text and date; per report a count and two dates. Deleting the account deletes its ratings. The admin listener's `GET /api/modules/<id>/reviews` (for the module detail view, #345) returns `{ module: { id, name }, summary, reviews: [{ id, stars, text, version, hidden, held, capped, seen, reports, author, authorId, createdAt, updatedAt, reply: { text, at } | null }] }`: every rating of the module, held and hidden ones too, newest first; 404 for a module the catalog doesn't know and nobody rated.
  - `GET /v1/catalog/lists/<revocations|blocks|successions>.json` returns a list signed offline with Tavora's catalogue key (revoked publisher keys with their allowlists, blocked zips, key successions), byte for byte as `pnpm tavora-catalog-sign` wrote it, or `404` before there is one. Cached for 5 minutes. The app checks the signature and the sequence number; the service never holds the catalogue key.
- **Conversations** (decided 2026-10-27, `conversations.ts`, `conversations.sqlite`; the design is "Conversations" in the review-and-contact design doc): two kinds only, a user writing to the developer of a published module and Tavora writing to an account. All routes need a sign-in, are never cached and take JSON of at most 8 KB; 30 writes an hour per client. `GET /v1/conversations` answers `{ conversations: [{ id, kind, role, module, type, label, title, state, closeReason, createdAt, lastMessageAt, closedAt, unread, previousId, closesInDays }], inbox: { open, unread, developer } }` (the other side only as `title`: "Developer of <module> (<developer name>)", "User · K7" or "Tavora"; never an account id, email, profile name or picture). `GET /:id` answers `{ conversation, messages }` and marks it read. `POST /` `{ moduleId, type: bug|feature|question, text, versions: { tavora, module }, previousId? }` starts one (`201`; refused with `404`, `403 own-module | contact-off (with link) | account-too-new (hours)`, `429 daily-limit (hours)` at 5 a day, `409 already-open (id)`, `400 message-link | message-words | bad-request`). `POST /:id/messages { text }` (50 a day per account), `POST /:id/close { outcome? }` (developer: fixed, added, not-planned, not-a-bug, none; the user's own close is `user`; `403` for a Tavora conversation), `POST /:id/block { report?: { reason, note? } }`, `POST /:id/report { reason: insults|hateful|spam|other, note? }`, `DELETE /:id`, `GET|PUT /settings { emailCopies }`. `GET|PUT /v1/catalog/modules/:id/contact { enabled, link }` is the developer's (an https link of at most 200 characters, `403 not-publisher` for anyone else); the module page answer carries `module.contact`. `GET /v1/texts` (public, 5 minutes) answers the texts the maintainer saved: `{ texts: { <key>: { en, de } } }`. The admin listener has `/api/messages` (Tavora's own conversations and the reported ones; `GET /:id` answers `403` for any other), `/api/messages/start|reply|close|reopen|dismiss-report` and `/api/texts`. An hourly sweep closes developer conversations idle for 30 days (`timeout`) and deletes closed ones after 180 days unless reported. Deleting an account closes its conversations with `left` and removes its message texts and reports. Email copies use the daily mail limit minus the reserved mails.
- **Leaderboards** (decided 2026-10-28, `leaderboards.ts`, `leaderboards.sqlite`; the design is "Puzzle games: leaderboards and names" in the vault's decisions), there while accounts are (`503 unavailable` otherwise). A module's boards are keyed by its id; a catalog module's run only once the admin allows it, and they are the ones its newest listed manifest declares. A development copy (`local.*`) needs no allowing, sends its board declaration itself (`kind`, `daily`, `order`, `minGames`), and each user sees only their own line there; an account keeps at most 10 of them. Reading needs no sign-in; a sign-in the service doesn't know is `401 signed-out`. 120 requests a minute per client, and 60 writes a minute per account and module. Five board kinds: `streak` (best and current winning streak; `daily`: one result a day, a missed day ends it), `score` (the best value, `order` high or low), `total` (the sum of values of 0 or more, with `games`), `average` (the mean, `order` high or low, with `games`) and `rate` (the share won, 0 to 100 with one decimal, with `games` and `wins`); `average` and `rate` list a user only from `minGames` results (10 by default, at most 1000). `GET /v1/leaderboards/<module>` answers `{ available, shown, name, label }` (`name` is the profile name the boards show, `null` for a pseudonym, then `label` such as `K7`). `PUT|DELETE /<module>/shown` shows the account on the module's boards or takes it off (deleting its results there; `403 not-allowed`). `POST /<module>/boards/<board> { results, board? }` takes 1 to 50 results, each on its own: `{ accepted: [id], rejected: [{ id, reason: invalid|time|archive|day-taken|full }] }` (`403 not-shown | not-allowed`, `404 unknown-board`). A result is `{ id: uuid, at, day, outcome: won|lost }` (streak, rate) or `{ id, at, day, value }` (score, total, average; a total's value is 0 or more); `day` is the user's local `YYYY-MM-DD` and is needed on every kind (`invalid` without). Ids are idempotent per board, a daily board keeps one result a day, and every result must have ended within its `day` (UTC−12 to UTC+14), otherwise `archive`, so an old puzzle replayed never counts. `at` is at most 5 minutes ahead and a year back, and an account keeps 10,000 results per module. **Periods:** every board can be read for `day`, `week` (Monday to Sunday), `month`, `year` or `all`; a result lands in the period that holds its `day`, and each period's line is worked out from that period's results alone (a streak too; streak boards have no `day` period). Results are kept, so past periods stay readable. `GET /<module>/boards/<board>?period=&day=&limit=` (development copies add `kind`, `daily`, `order`, `minGames`) answers `{ rows: [{ rank, of, name | label, self, ... }] }`, best first, equal lines sharing a rank, the reader's own line last when further down; the numbers are `current` and `best` (streak), `value` (score), `value` and `games` (total, average) or `value`, `games` and `wins` (rate). `period` is `all` by default (another value than the five: `400 bad-request`); `day` is any day up to tomorrow (the server's, `400` otherwise), picks the period that holds it, and is today by default; a daily streak is judged as of that day when it is within a day of the server's today. `of` is how many users the board has in that period. Ties: streak by best, then the running streak, then who got there first; score by value, then first; total by sum, then first; average by mean, then more games, then first; rate by share, then more games, then first. Suspended and banned accounts are left out. `GET /<module>/mine?day=&boards=` answers `{ boards: [{ id, periods: { day, week, month, year, all } }] }`, each period `{ rank, of, ...numbers }` or `null` (no line, under `minGames`, no `day` period on a streak, module not available, or signed out, which is still `200`). A catalog module's boards come from its listing; a development copy sends `boards` as a JSON list of at most 20 declarations `[{ id, kind, daily?, order?, minGames? }]` (`400` for bad JSON; entries with a bad id or kind are left out). The host adds each board's name. Names the word filter refuses, names the admin hid and empty names show as the label. Deleting an account deletes its rows. The tables are version 2 (`pragma user_version`); an older file is dropped and rebuilt. The admin listener has `GET|POST /api/leaderboards/modules` (`{ id, allowed }`) and `GET|POST /api/leaderboards/hidden-names` (`{ accountId, hidden }`).
- **Counting** (decided 2026-10-26), plain daily totals in `stats.sqlite`, nothing about who or from where (no address, no id, no request log; a user without an account is never counted as a person). `POST /v1/catalog/installed { id }` and `POST /v1/catalog/updated { id }` count a module install or update (only a listed module); `POST /v1/app/updated { version }` counts a finished app update (the app sends it only while online features are on). `GET /internal/installer-download` counts an installer download: the update feed's Caddy calls it (a `reverse_proxy` that throws its answer away; if the API is down or slow the installer is still served, only not counted; see `apps/desktop/deploy/tavora-updates.caddy`) and passes the file name in `X-Forwarded-Uri`; `api.mytavora.app` answers 404 for `/internal/`. The installers on the GitHub releases are counted apart (`app-installer-github`): GitHub only keeps a running total per file, so once an hour (on start, then hourly) the server reads every release of `wellbrained/tavora` (no token; 60 requests an hour are allowed) and counts what each version's `Tavora-Setup-<version>.exe` gained since the last look, on that day (the first look counts the whole total so far; the last totals are kept in `stats.sqlite`). Visits to mytavora.app: the page posts `POST /v1/site/visit` with `{ referrer }` when it opens and `{ click: "download"|"docs"|"github"|"privacy" }` when such a link is clicked, as plain text so the browser sends it without a CORS check; the service answers 204 whatever happens and counts only calls with `Origin: https://mytavora.app` whose user agent doesn't say bot (30 a minute per client). A view counts as `site-view` by the referring domain (www. left off; `direct` without one; the site's own pages count nothing) and as `site-country` by country code (`unknown` when not found), a click as `site-click` by link. The country comes from DB-IP's free country file (`dbip-country-lite.mmdb` in the state folder, CC BY 4.0, "IP Geolocation by DB-IP"), which the server fetches on start when missing and again when it is over a month old (checked daily); the address is only looked up, never kept. Once a day (UTC, on start and then hourly until it is written) the server writes the snapshot of accounts: all, active in 7 days and active in 30 days (a sign-in's `lastUsedAt`), as three numbers. Each kind keeps at most 500 different versions or modules a day. The admin listener has `GET /api/stats?days=<1-730>` (default 30, ending today) or `?from=&to=` as `YYYY-MM-DD`: `{ from, to, days: [...], counts: { "app-installer"|"app-installer-github"|"app-update"|"module-install"|"module-update"|"site-view"|"site-country"|"site-click": { "<version or module id>": [one number per day] } }, totals: { <kind>: { <key>: sum } }, accounts: [{ total, active7, active30 } | null per day] }`.
- 60 requests a minute per client, then `429` with `Retry-After`. No CORS: the app calls it from its main process.
- Every other answer is never cached. The service never logs a request, so what a user typed is not kept.

## The dataset

`pnpm --filter @tavora/api dataset` runs on a PC, never on the server. It merges:

1. the app's built-in games (`apps/desktop/src/main/catalog.ts`), which keep their ids,
2. Wikidata (CC0): video games with a Steam application ID (P1733), their English label and aliases,
3. optionally Steam's game list, when `STEAM_WEB_API_KEY` is set.

Wikidata is asked in ranges of Steam appids. When it is busy (429, 502, 504 or no answer) the script tries again up to three times, and splits a range that keeps failing in two.

`--limit <n>` stops after n Wikidata rows (for a quick test; do not commit its registry).

It writes `data/games.sqlite` (not in git) and updates `data/ids.tsv`.

### Ids are frozen

An id is a slug of the game's name, issued once. `data/ids.tsv` lists every id ever issued with its matching keys (`wd:Q…`, `steam:…`). A rebuild reads it first, so a renamed game keeps its id, a new game with the same name gets a suffix, and a game that dropped out of the sources keeps its id reserved. Commit the file after every real build and never edit it by hand. No id starts with `local-`: that prefix belongs to custom games on a user's PC.

## Hosted game icons

Logos only, never covers or artwork: the small icon each game uses itself, kept unchanged (an .ico is turned into a PNG without changing a pixel). Game names and icons belong to their publishers, and Tavora is not affiliated with them: the notice says so in every list, the app shows it wherever it shows the icons, and the website's privacy page repeats it. Icons come from users: they offer them, and they are served once approved. `data/icons` can still hold icons that ship in each release, but it is empty since the Blizzard icons were taken out (2026-10-27).

```sh
pnpm --filter @tavora/api icon add diablo-iv "Diablo IV|Diablo 4" path\to\Diablo.ico "where it came from"
pnpm --filter @tavora/api icon remove diablo-iv     # a publisher's takedown request
```

Commit `data/icons` and deploy with `scripts/Deploy-Api.ps1`. **A takedown request is met by removing the icon and deploying, the same day.** The service checks every file against its recorded hash and refuses anything that is not a small, well-formed PNG, so a damaged folder never serves a wrong file.

### Tavora Admin and reviewing what users offer

Offers wait in the state file until a person approves them. Tavora Admin (the old review page, grown into a panel) is a second, private listener (`ADMIN_PORT`, 127.0.0.1 only, never forwarded by Caddy) and every call needs the `ADMIN_TOKEN` in an `X-Admin-Token` header, so reaching it takes the server and the token.

```sh
tavora-api-set-setting admin-token      # on the server, once: prints a token to keep
```

The page is reached through an SSH tunnel to the server (for example `ssh -N -L 4011:127.0.0.1:4011 <server>`, then `http://127.0.0.1:4011/`); it asks for the admin token once per browser session. Anything that forwards it further must pass on the token the page sends and never add its own, or everyone who can reach the forwarder could approve or take down icons. The tailnet proxy keeps asking `GET /api/overview` for the offers waiting, so that answer (`{ pending, hosted }`) must stay as it is.

The panel lives in its own private repo, `wellbrained/tavora-admin` (Vue and the shared kit `@tavora/official-ui`, linked from this repo), built by Vite into plain files that the API serves from `TAVORA_ADMIN_DIR` (nothing inline, so the page's content security policy stays strict). It is deployed on its own and never travels with an API release; the JSON it reads stays here. Its sections:

- **Overview**: what waits for the maintainer (a list of kinds from `GET /api/summary`; a new kind is one line in `admin-panel.ts`) and the key numbers.
- **Updates** (show-only): the version on the update feed (`latest.yml` at updates.mytavora.app) and the patch notes of the app versions, each marked on the feed, not on the feed yet or earlier. The notes are the ones bundled into the API at its last release (`apps/desktop/src/shared/patch-notes.ts`), so "not on the feed yet" includes versions merged since.
- **Modules**: every catalog module, listed or not, with its newest version, installs from Browse, stored bytes, its versions, and **Unlist** / **List** (`POST /api/catalog/listed`), plus the catalog's storage against its limit.
- **Review**: the tabs below.
- **Accounts**: the counts (total, new per day, accounts with a sign-in used in the last 7 and 30 days) and, below them, the list of every account with search and the filters All, Developers, Banned and Suspended. A row expands to everything the service keeps about the account, unmasked, for the maintainer only: email, Discord name, profile, devices, developer name, linked keys, prefixes, publish tokens (name and dates, never the token), modules with installs, reviews written, cloud copy size and date, whether a key vault exists, and any ban or suspension with reason. Never a secret: no sign-in token, code or publish-token value or hash, and no vault bytes. **Suspend** is reversible (see Accounts: the maintainer's list and Suspend below). Deleting an account stays the owner's alone.
- **Status** (show-only): the API and the dataset's build date, emails sent today against the limit, when the last backup finished (the backup script leaves the time in `last-backup.txt` in the state folder; "Not reported" until the first backup after this release), catalog storage, whether mytavora.app, docs.mytavora.app and updates.mytavora.app answer, and each `@tavora/*` package's version on npm against the one on GitHub main (flagged when main is ahead). The server asks the outside world itself and keeps each answer for a minute.

A new section is a change in the panel's repo; new numbers for it go into the summary here.

Review has five tabs, **Needs review** (the default), **Hosted** (with a search box, and its pictures load only when opened, side by side, with a spinner until each one is there; the browser keeps each hosted picture under the hash of its file, so the next visit shows them at once) and **Reports**. Each tab is a list of rows: the logo, the name, a status badge and the buttons. Block, Take down, Unlist and Decline ask first in a dialog. **Needs review** shows each offered icon with **Approve**, **Deny** and **Block** (deny, refuse the same file for ever and every later offer from the account that sent it; a "custom game" badge marks a game a user added by name, which is published for exactly the name shown), plus **Approve all** and **Deny all** on top (each asks first, then goes through the offers one by one and skips any that fail) (a "has an icon" badge means the game already has one, and Approve is off; "replaces" means that icon is open for replacements, and Approve swaps it). Approving publishes the icon at once under the game's name and the name it was offered under, and drops the other offers for that game. **Hosted** shows the hosted icons with an approved or release badge, **Open for replacements** and **Close** (an open icon is served as before, but users may offer another for its game, and approving one replaces it; the new icon starts closed; `POST /api/replaceable { id, replaceable }`), **Take down** (a publisher's request, effective at once; a release icon also has to be removed with `pnpm --filter @tavora/api icon remove <id>` and deployed) and **Block** (take down and refuse the same file for ever). **Reports** lists the catalog modules users reported, most reported first, with an in catalog or hidden badge and the report count, and **Unlist** (out of the catalog at once; users who installed it keep it), **List** and **Dismiss**. **Reviews** lists reported reviews with **Hide**, **Show** and **Dismiss**. **Keys** lists the developers' requests to replace a lost or leaked publisher key (old and new key, account, email, developer name, when it was asked, and when the new key was linked, red when that was less than a day before the request), with **Decline** for a waiting one. Its **successions.json** and **revocations.json** buttons download every entry in force now plus the waiting ones; a new revocation allows the zips the catalog took from that key before the request, so take out any that look wrong. Sign each file offline with `pnpm tavora-catalog-sign successions|revocations <file> --key <catalogue key> --out <signed file>` and serve it with `tavora-api-catalog set-list`; a request shows as done, in the app too, once the served lists hold it. To turn a module off on users' PCs, block its zip or revoke its key in a list signed offline with `pnpm tavora-catalog-sign` and serve it with `tavora-api-catalog set-list`. An approved icon wins over a release icon of the same game, and a takedown of a release icon stays in force until it is deployed away.

Set where publishers send removal requests with `tavora-api-set-setting takedown` on the server; hosted icons are only served while it is set.
## Module catalog

Developers publish with `tavora-pack publish` (above). The maintainer can also add modules by hand:

```sh
pnpm --filter @tavora/api catalog add path/to/module.zip   # packed and signed with tavora-pack
pnpm --filter @tavora/api catalog delist <module id>       # out of the catalog; its versions are kept
pnpm --filter @tavora/api catalog relist <module id>
pnpm --filter @tavora/api catalog list
pnpm --filter @tavora/api catalog set-list revocations path/to/revocations.json   # also blocks, successions
```

On the server the same commands are `tavora-api-catalog` (copy the zip there first). A zip is checked the way the app's installer checks it before anything is stored: size and compression caps, a valid manifest with every page and icon it names, a valid changelog if it has one, and a publisher signature over every file. Unsigned zips and `tavora.` ids are refused. A module's first version sets its owner key; later versions must come from the same key and be newer, so no version is ever replaced. Zips are stored as `catalog/zips/<sha256>.zip` and are never unpacked on the server.

### Review before listing

Decided 2026-10-26 (the "Tavora Admin panel" entry in the vault's decisions). Every new version runs the automatic checks in `src/moderation.ts`; when they all pass it is listed at once, as before. When any fails, it is not listed: its zip stays in the catalog folder (served to nobody), a row with status `waiting` and the reasons is kept, and a person decides. **Nothing is ever approved automatically**, and a check that cannot run counts as failed.

| Check | Waits when |
| --- | --- |
| `words` | The word filter (`review-filter.ts`: slurs plus adult/18+ terms; links are fine) finds something in the name, any description or translation, panel and action names, the changelog, or the readme |
| `permissions` | A module's first version asks for network hosts or connectors, or an update asks for a host or connector the last listed version didn't |
| `copy` | The name is like another publisher's listed module (the same letters and digits, or one letter off for names of 6 or more), or at least 80% of the files' bytes (same hashes, 1 KB or more in all) are in another publisher's listed version |
| `code` | A script, page or SVG in the zip has `eval`, `new Function` or a string given to `setTimeout`, WebAssembly (a `.wasm` file too), a dynamic `import()` of an address or something computed, a script added at run time or loaded from another address, or reads as packed or obfuscated (`_0x…` names, `eval(function(p,a,c,k,e,d)`, many escapes, JSFuck, a big `atob` payload); a code file over 8 MB is not read, which also counts |
| `virus` | ClamAV finds something, **or cannot run**: no scanner set, clamd not answering, an error reply, a file clamd can't take whole (over 20 MB) or taking too long |

Two more reasons make a version wait whatever the checks say: `first-module` (the account has never had a version approved or listed; accounts that already had a listed version or a listed module under one of their keys count as approved) and `pictures` (an icon or screenshot that is new or changed since the last listed version). Each reason has a short text for the developer and a detail for the maintainer (what matched, in which file). Versions that wait don't count for the copy checks, are never handed out, reported, counted or served, and keep their prefix reserved. Declining or withdrawing deletes the zip and any picture no other version uses; a declined zip's hash is remembered, so exactly that zip is refused (`declined`).

The admin app (`ADMIN_PORT`, token as for the rest) answers JSON under `/api/moderation/*`; the Approval section of the review page is built on it:

| Call | What it does |
| --- | --- |
| `GET /waiting` | Versions waiting, oldest first: reasons with details, the developer (name, email, keys, prefixes, modules, whether approved before or banned), the module (descriptions, translations, permissions, notes, readme, pictures, file list) and the last listed version. `reasons` lists the decline reasons |
| `GET /waiting/<sha256>/file?name=<path>` | A file of the waiting zip as plain text (first 1 MB), to read its code |
| `GET /pictures/<sha256>.<png or webp>` | An icon or screenshot of a waiting version |

**Accounts: the maintainer's list and Suspend** (decided 2026-10-26, `accounts-admin.ts`). The admin app answers JSON under `/api/accounts/*`, behind the admin token like everything else (`GET /api/accounts` stays the counts):

Its modules stay listed, and replies it wrote as a publisher under other users' reviews stay visible. The person is emailed the reason in English or German (the language of their last published version, else English; `mailed`; nothing is sent to a Discord-only account). 404 for an unknown account. | `POST /unsuspend { id }` | Reverses all of it except the deleted sign-ins: the person signs in again. The reviews the suspension hid show again (`shownReviews`); one a person hid on its own stays hidden. 404 if the account isn't suspended and no review is left to show; safe to repeat |

| Call | What it does |

| `GET /blocks.json` | The entries for `pnpm tavora-catalog-sign blocks`: every block in force, then the ones to sign. Sign it on your PC, upload with `catalog set-list blocks`; a block then shows as in force |

Emails to developers go out through the same mailer as the publish emails, never with the allowance kept for sign-in codes; a mail that can't go out doesn't undo the decision.

**What the server needs:** ClamAV with clamd and fresh signatures. `tavora-api-clamav` on the server (copied there by `Deploy-Api.ps1`) installs `clamav-daemon`, `clamav-freshclam` and `socat`, downloads the signatures, adds the service's user to the `clamav` group, waits until clamd answers and runs `tavora-api-set-setting clamav`, which sets `CLAMD_SOCKET=/var/run/clamav/clamd.ctl` and restarts the service. clamd needs about 1 GB of memory while it holds its signatures, so check the server has the room; the service keeps its 256 MB limit because it only streams files to clamd. `tavora-api-clamav status` shows whether clamd answers. Until then every new version waits for review (the log says so at start). Set `MAINTAINER_EMAIL` too, or nobody is told when a version waits.

## Backups

`tavora-api-backup.timer` (daily, 03:15 UTC) runs `/usr/local/sbin/tavora-api-backup`: consistent copies of `accounts.sqlite`, `icons.sqlite`, `reviews.sqlite`, `conversations.sqlite`, `leaderboards.sqlite` and `catalog.sqlite`, plus the catalog's zips (SQLite's backup, safe while the service runs) packed into `/srv/tavora-api/backups/tavora-api-<time>.tar.gz`, 14 days kept, no secrets (`production.env` is not in it). `Deploy-Api.ps1` installs the script and the timer with every release. Copy them off the server regularly; a backup that only lives on the server does not survive losing it. To restore: stop `tavora-api`, unpack a backup into `/var/lib/tavora-api` (owner `tavora-api`, mode 600), start it again.
