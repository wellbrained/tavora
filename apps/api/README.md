# @tavora/api

Tavora's online game database: a small read-only service that answers game searches from its own dataset. The app asks it; it never calls Wikidata or Steam while running. The only player data it holds is accounts (an email address and its sign-ins), and only once it can send email.

Needs Node 22.18 or newer (it runs the TypeScript directly and uses `node:sqlite`).

## Run it

```sh
pnpm --filter @tavora/api dataset      # build data/games.sqlite (see below)
pnpm --filter @tavora/api dev          # http://127.0.0.1:4010, restarts on changes
```

| Variable | Default | Meaning |
| --- | --- | --- |
| `PORT` | `4010` | Port, always bound to 127.0.0.1 |
| `TAVORA_GAMES_DB` | `data/games.sqlite` | Dataset to load, opened read-only |
| `STEAM_WEB_API_KEY` | unset | Enables the Steam import. On the server it lives in `/srv/tavora-api/shared/production.env` (set with `deploy/tavora-api-set-steam-key.sh`, never committed). Without it search works and the import answers 503 |
| `TRUST_PROXY` | unset | `1` behind Caddy: the client is the first `X-Forwarded-For` address, for the rate limit |
| `TAKEDOWN_CONTACT` | unset | Where a publisher asks for an icon to be removed (an address or a link). Hosted icons are only served while it is set. On the server it lives in `/srv/tavora-api/shared/production.env` |
| `TAVORA_ICONS_DIR` | `data/icons` | The hosted icons: `<id>.png` files and their `index.json`. In a release it is the `icons` folder next to `server.mjs` |
| `TAVORA_STATE_DIR` | `data/state` | The one writable place: icons players offered, approved ones and takedowns (`icons.sqlite`), accounts (`accounts.sqlite`), their cloud copies (`copies.sqlite`, not in the daily backup), and the module catalog (`catalog/`). On the server it is `/var/lib/tavora-api` (systemd `StateDirectory`) |
| `ADMIN_TOKEN` | unset | At least 24 characters. Starts the private review page; without it nothing offered can be approved. Make it with `tavora-api-set-setting admin-token` on the server |
| `TAVORA_TEST_INBOX_PORT` | unset | Development only, ignored when `NODE_ENV=production`: turns accounts on with a test inbox that keeps mail in memory and shows it on `http://127.0.0.1:<port>` (`GET /mails` as JSON, `DELETE /mails` empties it). Without it, and until a mail provider is set up, accounts are off and answer 503 |
| `BREVO_API_KEY` | unset | Turns accounts on in production: sign-in emails go through Brevo's transactional API. On the server it lives in `/srv/tavora-api/shared/production.env`, set with `tavora-api-set-setting brevo-key` on the server, typed in by hand. Brevo only accepts the key from the server's own addresses (authorised IPs); a new server address must be added there first, or every email fails with `mail-failed` |
| `MAINTAINER_EMAIL` | unset | Who hears by email, at most once a day, when the module catalog is full and refuses uploads with 507. Needs accounts (an email provider). Without it only the review page shows it. Set it with `tavora-api-set-setting maintainer-email` on the server |
| `MAIL_FROM` | `signin@mytavora.app` | The sender of those emails; its domain is authenticated in Brevo (DKIM `brevo1`/`brevo2._domainkey`, DMARC, the `brevo-code` TXT) |
| `MAIL_DAILY_LIMIT` | `300` | Emails a day (UTC), Brevo's free plan. The last 20 are kept for changing the address and deleting an account; after that the account routes answer `503 daily-limit` with `retryAt` |
| `ADMIN_PORT` | `4011` | The review page's port, always on 127.0.0.1 and never forwarded by the web server |

## API

- `GET /v1/games/search?q=<text>&limit=<1-20>` returns `{ "results": [{ "id": "elden-ring", "name": "Elden Ring", "steamAppId": 1245620 }] }` (`steamAppId` is `null` for games without one; the app uses it to fetch the game's icon from Steam itself), best match first: exact name, exact alias, name prefix, alias prefix, then every word as a word start. Case, accents and apostrophes are ignored. `q` is at most 100 characters, `limit` defaults to 8.
- `GET /v1/health` returns `{ ok, games, builtAt }`.
- `POST /v1/steam/library` with JSON `{ "profile": "<steamcommunity.com profile link or SteamID64>" }` returns `{ "games": [{ "appid": 1245620, "name": "ELDEN RING", "id": "elden-ring" }] }`, sorted by name; `id` is the canonical id when the dataset knows that Steam appid, otherwise `null`. The service asks Steam's Web API with its own key, passes the list straight back and stores nothing. 400 for a profile it cannot read, 404 for an unknown custom name, 502 when Steam fails or the profile's Game details are private, 503 without a key, 415 unless the body is JSON. 6 requests a minute per client. It is a POST so the profile is in no URL.
- `GET /v1/icons` returns `{ "notice": "…", "takedown": "<contact>", "icons": [{ "id": "diablo-iv", "names": ["Diablo IV", "Diablo 4"], "sha256": "…", "size": 9527 }] }` and `GET /v1/icons/<id>.png` the icon itself (a PNG of at most 256 px). 503 and 404 while `TAKEDOWN_CONTACT` is not set. The app downloads the list, matches it on the player's PC and asks only for the icons it needs, so the service sees which icons are asked for, one request each, and nothing else (no log is kept). These two are the only answers that may be cached (5 minutes for the list, a day for a file).
- `POST /v1/icons/submit` with `Authorization: Bearer <token>` (a signed-in account) and JSON `{ "id": "diablo-iv", "name": "Diablo IV", "source": "installed", "icon": "<base64 PNG or .ico>" }` offers an icon the player's PC has and the service lacks. The id must be a game in the dataset that has no icon yet, or a `local-` id for a game the player added by name: then `name` decides. A name the dataset knows for exactly one game is offered for that game; a name no game has is offered as a custom game, listed under `local-<slug of the name>` and matched by that name only; a name several games share is refused. The file must be a PNG or an .ico of 32 to 256 px and at most 200 KB. It is cleaned (a PNG keeps only the chunks that make the picture), queued and answered `202 { "status": "received" }`, the same for a new offer, a repeat, a blocked file and a blocked account. Nothing is served until a person approves it. The account that sent an offer is kept with it until it is approved or denied, and an account whose offer was blocked is refused from then on. `400` for what is not an icon offer, `401 signed-out` without a valid sign-in, `409` when the game already has an icon, `413` over 400 KB, `415` unless the body is JSON, `429` with 100 offers from the account already waiting, `503` while `TAKEDOWN_CONTACT` is not set, without accounts, or while the queue is full. 100 offers an hour per client.
- **Accounts** (`/v1/account`). An account is an email address; the player signs in with a 6-digit code sent to it, never a password. JSON bodies only; errors are `{ error, reason }`, and the app translates `reason` (`bad-email`, `bad-request`, `wrong-code`, `too-many`, `daily-limit`, `mail-failed`, `signed-out`, `same-email`, `email-taken`, `not-found`, `unavailable`). All of it answers `503` while the service cannot send email.
  - `POST /code { email, language }` mails a code (`language` is `en` or `de`) and answers `202 { "status": "sent" }`, the same whether or not the address has an account. A code lasts 10 minutes, a new one replaces the last, 5 wrong tries spend it; one address gets at most 3 codes in 15 minutes and 10 a day (all purposes together), and a client may ask 10 times an hour.
  - `POST /verify { email, code, os, create }` signs in. For an address with an account it answers `{ status: "signed-in", token, device, account }`. For a new address it answers `{ status: "no-account" }` and keeps the code, so the app can ask the player; the same call with `create: true` makes the account (`status: "created"`). `os` is `windows`, `linux`, `macos` or anything else (kept as `other`). A client may check 20 codes in 15 minutes.
  - Signed in, with `Authorization: Bearer <token>`: `GET /` returns `{ account: { email, createdAt }, devices: [{ id, os, name, createdAt, lastUsedAt, current }] }`; `POST /sign-out` ends this sign-in; `PUT /devices/<id>/name { name }` renames one (at most 40 characters; a sign-in may send its `name` too); `DELETE /devices/<id>` ends another; `POST /email/code { email, language }` and then `POST /email { email, code, language }` change the address (the code goes to the new one, a notice to the old one, and `409 email-taken` comes only after the right code); `POST /delete/code { language }` and then `POST /delete { code }` delete the account and every sign-in at once. A token unused for a year stops working. `GET /profile` returns `{ profile: { name, initials, picture, updatedAt } | null }` and `PUT /profile` with the same fields keeps it unless the account already has a newer one (`updatedAt`, never later than now), answering with what the account has; `picture` is a base64 PNG of 256 px and at most 512 KB, or `null`; the name is at most 32 characters, the initials 3. The profile is only ever shown to its owner.
  - **Discord login** (decided 2026-10-16), a second sign-in method; an account has an email, a Discord login or both, never none. The app runs Discord's browser sign-in itself (PKCE, scope `identify`, back to `http://127.0.0.1:53682/discord`) and sends `{ code, verifier }`; the service exchanges them with Discord (public client, no secret), reads the user id and username, revokes the token and keeps neither it nor anything else. `POST /discord/sign-in { code, verifier, os }` signs a known login in (refreshing its username) or answers `{ status: "no-account", ticket, discord: { name } }`, holding the checked login for 10 minutes; `POST /discord/create { ticket, os }` then makes a Discord-only account. Signed in: `POST /discord { code, verifier }` connects Discord (`409 discord-taken` when another account has it: never merged, never linked by email), `DELETE /discord` and `DELETE /email` remove a method (`409 last-method` for the last one), `POST /delete/discord { code, verifier }` deletes an account by a fresh sign-in with its own Discord login (`/delete/code` answers `409 no-email` without an address). Answers show `discord: { name } | null`, never the Discord id. Errors also `discord-refused` (400), `discord-unreachable` (502), `discord-expired`, `discord-mismatch`.
  - **Module developer**, signed in: `GET /developer` returns `{ developer: { name, changedAt, nextChangeAt } | null, keys: [{ fingerprint, linkedAt }], requests: [{ old, new, leaked, requestedAt, status }] }` (`status` is `waiting`, `done` once the served signed lists hold it, or `declined`); `PUT /developer { name }` sets the public developer name (3 to 32 letters, digits, spaces, dots, dashes or underscores; unique when case and those separators are ignored; never one containing "tavora" or a reserved word; it changes once in 30 days, and a name given up stays blocked for other accounts for 30 days; errors `bad-name`, `name-taken`, `name-reserved`, `name-too-soon` with `nextChangeAt`); `POST /keys/code` gives a one-time code `{ code, expiresAt }` (8 characters, 10 minutes, a new one replaces the last; `409 no-developer-name` without a name); `POST /keys/<fingerprint>/replace { new, leaked, language }` asks to replace a lost (or leaked) linked key with another key linked to the same account, for the maintainer to sign offline from the review page, and emails the account's address (`404 not-found` unless both are linked here, `409 key-in-request` while another replacement for it waits); `DELETE /keys/<fingerprint>` unlinks a key (`409 key-in-request` while it is part of a waiting replacement).
  - Kept: the address, when the account was made, the profile (name, initials, picture, when it changed), a Discord login's user id and username, the developer name and when it changed, the public halves of linked publisher keys, and per sign-in a hash of its token, the operating system and two dates. Codes and the per-address counters are kept under a hash of the address and are gone within a day. No connection address and no PC name is stored.
  - **Cloud copy** (decided 2026-10-19), signed in, under `/v1/account/copy`: one copy of the player's Tavora data per account, which only the player can read. The app encrypts everything on the PC before it leaves, with a key the service never sees; the service holds opaque **parts** (each named by a 32-byte id the app derives with that key, so equal content is stored once and no id says which file it is) and an encrypted **manifest** saying which parts make the copy. Bodies are `application/octet-stream` (415 otherwise), so a web page cannot send one without a preflight. `GET /` returns `{ copy: { version, size, updatedAt } | null, limit }`; `GET /manifest` the manifest's bytes with `X-Copy-Version` (`404 no-copy`); `POST /parts` stores parts, one after another as a 32-byte id, a 4-byte big-endian length and the bytes (a part at most 4 MB plus 1 KB, about 8 MB per upload), answering `{ stored }`; `POST /parts/get` with ids one after another (at most 2048) answers the parts it has in the same framing, in the order asked, about 8 MB at most and always at least one; `PUT /` with the version it started from and the part count (4 bytes each, big-endian), the part ids and then the manifest makes a new version and answers `{ version, size }`, or `409 copy-changed` with the current `version` when another PC saved one first, `409 missing-parts` with how many, or `413 copy-full`; `DELETE /` removes the copy at once; a new copy's versions go on from the deleted one's, so a PC that missed the delete can't write over it. A copy is at most 100 MB (the manifest and the parts it uses); while a new version uploads, the parts kept may reach 200 MB, then `413 copy-full`. Parts no version uses are dropped when a new version is saved. Deleting the account deletes the copy. 300 requests a minute per client. Kept: the parts, the manifest, the version, its size and when it changed, in `copies.sqlite`, which the daily backup leaves out (after a loss the PCs upload again). `503 unavailable` without accounts.
  - **Key vault** (decided 2026-10-20), signed in, under `/v1/account/vault`: one small sealed blob per account, opened only by the player's recovery key (the same key as the cloud copy, under its own derived key). Its being there tells a new PC that the account already has a recovery key. `GET /` returns its bytes with `X-Vault-Version` (`404 no-vault`); `PUT /` with the version it started from (4 bytes, big-endian) and the sealed bytes (at most 64 KB) answers `{ version }`, or `409 vault-changed` with the current `version`; `DELETE /` removes it. Bodies are `application/octet-stream` (415 otherwise). Kept in the accounts database, so the daily backup has it; deleting the account deletes it. 60 requests a minute per client.
- **Publishers** (`/v1/publishers`), there while accounts are. `GET /<fingerprint>` returns `{ name }`, the developer name of the account a publisher key is linked to (`404 unknown` otherwise; cached publicly for an hour), and nothing else about the account. `POST /link { code, publicKey, signature }` links a key: `publicKey` is the raw 32-byte Ed25519 key in base64 and `signature` its signature over `tavora-key-link-1\n<code>`, which `tavora-pack link` makes; the signature is checked before the code is used up, so only whoever holds the key can link it. Answers `{ status: "linked", fingerprint, name }`; errors `bad-signature`, `wrong-code`, `key-taken` (another account's key), `too-many-keys` (20 per account). Link attempts count with code checks: 20 in 15 minutes per client.
- **Module catalog** (`/v1/catalog`), read-only, no sign-in (Milestone E; the threat model is `docs/catalog-threat-model.md` in the vault). Community modules only; Tavora's own stay bundled with the app. An entry is a module at its newest version: `{ id, name, description, version, minTavora, games, workspaces, permissions: { network, connectors }, owner, publisher, zip: { sha256, size }, publishedAt, notes }`. `owner` is the publisher key's fingerprint; `publisher` is the developer name of the account that key is linked to, or `null`, never a name the module claims. `notes` are that version's lines from the module's changelog, plain text.
  - `GET /v1/catalog` returns `{ modules: [entry] }`, every listed module; `?game=<id>` only those for that game and for any game; `?workspace=1` only those a personal workspace offers. The app takes a whole index and decides on the PC what to update, so it never sends what a player has installed. Cached publicly for 5 minutes.
  - `GET /v1/catalog/modules/<id>` returns `{ module: entry, versions: [{ version, publishedAt, notes }] }`, newest first.
  - `GET /v1/catalog/zips/<sha256>.zip` returns a listed module's zip, named by its hash and cached for a year. The app checks the hash and then installs it exactly like Install from zip; the service is never what makes a zip trusted.
  - `POST /v1/catalog/publish` with the zip as `application/zip` (at most 50 MB) and `X-Tavora-Signature`: the publisher key's Ed25519 signature (base64) over `tavora-catalog-publish-1`, a newline and the zip's SHA-256 in hex. `tavora-pack publish` sends it. No sign-in: the key that signed the zip must be linked to an account, and the upload signature must be that key's, so a zip shared by hand cannot be published by whoever got it. The account must hold the id's prefix (the part before the first dot), which it gets the first time it publishes under a free one: at most 3 per account, and none that a developer name could not be (`tavora`, `official`, `local` and the other reserved words). The zip is checked like a hand-added one, then listed at once (no review before listing; a person looks only at reported modules). Answers `201 { status: "published", id, version, sha256 }`, or `{ error, reason }` with `reason` one of `invalid` (400, `error` says why), `key-not-linked`, `bad-signature`, `prefix-taken`, `prefix-reserved`, `too-many-prefixes` (403), `key-revoked` (403: the signed revocation list revokes the key), `key-leaked` (403: the key's account reported it as leaked and the request wasn't turned down), `conflict` (409: an older or same version, or the id belongs to another key), `daily-limit` (429: 10 versions an account in 24 hours), `account-full` (413: 200 MB of zips an account), `too-big` (413), `catalog-full` (507: the review page shows since when, and `MAINTAINER_EMAIL` gets an email at most once a day, until an upload fits again), `too-many` (429: 30 uploads an hour per client) or `unavailable` (503, without accounts). A module's versions come from the key of its first version, or from a key that succeeds it by the signed successions list in the same account (the succession's `account` is the account id in `accounts.sqlite`); the listing's `owner` is the key that signed its newest zip, which the app checks the zip against. The service checks the stored revocation and succession lists against Tavora's catalogue public key itself, so a list put on the server without the catalogue key changes nothing. Prefixes stay held when an account is deleted, so nobody can publish new modules under its name; the maintainer can release one by hand.
  - `POST /v1/catalog/report { id, owner, sha256 }` (JSON, exactly these three fields, at most 500 bytes) records that a player pressed Report on a listed zip: the module id, its key's fingerprint and the zip's hash, and nothing about the player. Reports hide nothing; they wait on the review page, where a person decides. The publisher gets an email at most once a day when their key's account has an address, and only while more than the emails kept for sign-in codes are left that day. Answers `202 { status: "received" }`, `404` for a zip the catalog does not list under that id and key, `400`, `415`, `429` (10 reports an hour per client) or `503`.
  - `GET /v1/catalog/lists/<revocations|blocks|successions>.json` returns a list signed offline with Tavora's catalogue key (revoked publisher keys with their allowlists, blocked zips, key successions), byte for byte as `pnpm tavora-catalog-sign` wrote it, or `404` before there is one. Cached for 5 minutes. The app checks the signature and the sequence number; the service never holds the catalogue key.
- 60 requests a minute per client, then `429` with `Retry-After`. No CORS: the app calls it from its main process.
- Every other answer is never cached. The service never logs a request, so what a player typed is not kept.

## The dataset

`pnpm --filter @tavora/api dataset` runs on a PC, never on the server. It merges:

1. the app's built-in games (`apps/desktop/src/main/catalog.ts`), which keep their ids,
2. Wikidata (CC0): video games with a Steam application ID (P1733), their English label and aliases,
3. optionally Steam's game list, when `STEAM_WEB_API_KEY` is set.

Wikidata is asked in ranges of Steam appids. When it is busy (429, 502, 504 or no answer) the script tries again up to three times, and splits a range that keeps failing in two.

`--limit <n>` stops after n Wikidata rows (for a quick test; do not commit its registry).

It writes `data/games.sqlite` (not in git) and updates `data/ids.tsv`.

### Ids are frozen

An id is a slug of the game's name, issued once. `data/ids.tsv` lists every id ever issued with its matching keys (`wd:Q…`, `steam:…`). A rebuild reads it first, so a renamed game keeps its id, a new game with the same name gets a suffix, and a game that dropped out of the sources keeps its id reserved. Commit the file after every real build and never edit it by hand. No id starts with `local-`: that prefix belongs to custom games on a player's PC.

## Hosted game icons

Logos only, never covers or artwork: the small icon each game uses itself, kept unchanged (an .ico is turned into a PNG without changing a pixel). Game names and icons belong to their publishers, and Tavora is not affiliated with them: the notice says so in every list, the app shows it wherever it shows the icons, and the website's privacy page repeats it. The icons live in `data/icons` and ship in each release.

```sh
pnpm --filter @tavora/api icon add diablo-iv "Diablo IV|Diablo 4" path\to\Diablo.ico "where it came from"
pnpm --filter @tavora/api icon remove diablo-iv     # a publisher's takedown request
```

Commit `data/icons` and deploy with `scripts/Deploy-Api.ps1`. **A takedown request is met by removing the icon and deploying, the same day.** The service checks every file against its recorded hash and refuses anything that is not a small, well-formed PNG, so a damaged folder never serves a wrong file.

### Reviewing what players offer

Offers wait in the state file until a person approves them. The review page is a second, private listener (`ADMIN_PORT`, 127.0.0.1 only, never forwarded by Caddy) and every call needs the `ADMIN_TOKEN` in an `X-Admin-Token` header, so reaching it takes the server and the token.

```sh
tavora-api-set-setting admin-token      # on the server, once: prints a token to keep
```

The page is reached through an SSH tunnel to the server (for example `ssh -N -L 4011:127.0.0.1:4011 <server>`, then `http://127.0.0.1:4011/`); it asks for the admin token once per browser session. Anything that forwards it further must pass on the token the page sends and never add its own, or everyone who can reach the forwarder could approve or take down icons.

The page has four tabs, **Needs review** (the default), **Hosted** (with a search box, and its pictures load only when opened, side by side, with a spinner until each one is there; the browser keeps each hosted picture under the hash of its file, so the next visit shows them at once) and **Reports**. Each tab is a compact grid of rows: the logo, the name, a status badge and the buttons. **Needs review** shows each offered icon with **Approve**, **Deny** and **Block** (deny, refuse the same file for ever and every later offer from the account that sent it; a "custom game" badge marks a game a player added by name, which is published for exactly the name shown), plus **Approve all** and **Deny all** on top (each asks first, then goes through the offers one by one and skips any that fail) (a "has an icon" badge means the game already has one, and Approve is off). Approving publishes the icon at once under the game's name and the name it was offered under, and drops the other offers for that game. **Hosted** shows the hosted icons with an approved or release badge, **Take down** (a publisher's request, effective at once; a release icon also has to be removed with `pnpm --filter @tavora/api icon remove <id>` and deployed) and **Block** (take down and refuse the same file for ever). **Reports** lists the catalog modules players reported, most reported first, with an in catalog or hidden badge and the report count, and **Hide** (out of the catalog at once; players who installed it keep it), **Show** and **Dismiss**. **Keys** lists the developers' requests to replace a lost or leaked publisher key (old and new key, account, email, developer name, when it was asked, and when the new key was linked, red when that was less than a day before the request), with **Decline** for a waiting one. Its **successions.json** and **revocations.json** buttons download every entry in force now plus the waiting ones; a new revocation allows the zips the catalog took from that key before the request, so take out any that look wrong. Sign each file offline with `pnpm tavora-catalog-sign successions|revocations <file> --key <catalogue key> --out <signed file>` and serve it with `tavora-api-catalog set-list`; a request shows as done, in the app too, once the served lists hold it. To turn a module off on players' PCs, block its zip or revoke its key in a list signed offline with `pnpm tavora-catalog-sign` and serve it with `tavora-api-catalog set-list`. An approved icon wins over a release icon of the same game, and a takedown of a release icon stays in force until it is deployed away.

Set where publishers send removal requests with `tavora-api-set-setting takedown` on the server; hosted icons are only served while it is set.
## Module catalog

Developers publish with `tavora-pack publish` (above). The maintainer can also add modules by hand:

```sh
pnpm --filter @tavora/api catalog add path/to/module.zip   # packed and signed with tavora-pack
pnpm --filter @tavora/api catalog delist <module id>       # out of the catalog; its versions are kept
pnpm --filter @tavora/api catalog relist <module id>
pnpm --filter @tavora/api catalog list
pnpm --filter @tavora/api catalog set-list revocations path/to/revocations.json   # also blocks, successions
```

On the server the same commands are `tavora-api-catalog` (copy the zip there first). A zip is checked the way the app's installer checks it before anything is stored: size and compression caps, a valid manifest with every page and icon it names, a valid changelog if it has one, and a publisher signature over every file. Unsigned zips and `tavora.` ids are refused. A module's first version sets its owner key; later versions must come from the same key and be newer, so no version is ever replaced. Zips are stored as `catalog/zips/<sha256>.zip` and are never unpacked on the server.

## Backups

`tavora-api-backup.timer` (daily, 03:15 UTC) runs `/usr/local/sbin/tavora-api-backup`: consistent copies of `accounts.sqlite`, `icons.sqlite` and `catalog.sqlite`, plus the catalog's zips (SQLite's backup, safe while the service runs) packed into `/srv/tavora-api/backups/tavora-api-<time>.tar.gz`, 14 days kept, no secrets (`production.env` is not in it). `Deploy-Api.ps1` installs the script and the timer with every release. Copy them off the server regularly; a backup that only lives on the server does not survive losing it. To restore: stop `tavora-api`, unpack a backup into `/var/lib/tavora-api` (owner `tavora-api`, mode 600), start it again.

## Tests

`pnpm test` at the repository root. The tests use in-memory datasets and need no network.
