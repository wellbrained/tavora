# Security model

Tavora runs modules written by other people on users' PCs, next to their games. This page says what the host guarantees, how a module is kept inside its panel, and what is not covered. It describes the desktop host as it is today, and the guarantees are tested in the repository's gate tests (`apps/desktop/test/e2e`).

The attacker assumed throughout is a module whose author is hostile, or whose dependencies were compromised. It controls all the JavaScript, HTML and CSS in its own bundle and can send any message over its bridge port. It does not control the host or other modules.

To report a problem, see [Security policy](https://github.com/wellbrained/tavora/blob/main/SECURITY.md).

## How a module runs

- The **main process** is the only part with access to the operating system. It checks every message a module sends.
- The **host UI** (library, docking, Settings) is trusted code, but it is still sandboxed and has no Node access.
- Every **module** is untrusted. Each module gets, per workspace, its own browser session, its own origin (`tavora-module://<module id>/`) and its own renderer process, separate from the host and from other modules. It runs with `sandbox` and `contextIsolation` on, without Node and without `<webview>`.
- When you double-click the line between two panels, the main process measures how far each panel's page scrolls, to fit it. The script runs in an isolated world of its own, so the page's scripts can't change it, only reads sizes, and passes back two numbers (0 to 4000 px). It is the same for module pages and Browser panel pages.

## What a module cannot do

| | Guarantee |
| --- | --- |
| G1 | Reach Node, Electron or operating-system APIs. The module preload exposes nothing but the bridge port. |
| G2 | Read or write another module's data. Host storage is keyed by the module's bound identity, and web storage lives in separate sessions. |
| G3 | Choose or fake which module it is or which workspace it runs in. The host binds both when it creates the port; message fields never carry identity. |
| G4 | Use the network on its own. Everything but its own origin is blocked; hosts the user granted are reached only through host-controlled `network.fetch` and `network.readPage`. |
| G5 | Take down Tavora or other panels. A crash, hang or failed load is shown in that panel only, with Reload and Stop, and saved data is written atomically. |
| G6 | Read arbitrary files outside its own bundle. Only files the user explicitly picked can be reread through scoped, read-only references, and only folders the user allowed can be listed and read, read-only and within the extensions the manifest names (see [Folders on this PC](#folders-on-this-pc)); asset paths are resolved inside the module's folder; `..`, encoded `..`, links out and null bytes are refused. |
| G7 | Open windows, navigate away, download files or ask for devices (camera, microphone, location). |
| G8 | Exhaust the host through the bridge. Messages are plain JSON only, at most 8 MiB each, with at most 64 requests and 16 MiB in flight; an oversized message is refused inside the module's own renderer before the main process sees it. The main process counts these per panel, across every bridge port its pages ask for, so asking for a new port or reloading resets no limit: the new port starts with what the old one still runs. A port that closes starts nothing more, and its `network.fetch` and `network.readPage` requests end at once. When a panel closes, its page is hidden at once and keeps its port for at most a second, answering only its saves (settings, documents, files and panel state), so what was typed just before is kept; then the page closes. A page gets at most one new port every 250 ms; asking sooner waits for it. Settings, documents and panel state have quotas. |
| G9 | Use a capability the user did not grant. Gated calls check the user's grant first, on every call, and answer `PERMISSION_DENIED` otherwise. |
| G10 | Run code through its icon. Icons are PNG or WebP files inside the package, at most 256 KB, checked by their signature and shown as a plain picture. |
| G11 | Fill the disk through its own browser storage. Past 256 MB (or 5,000 files) in one workspace, the host ends the module's renderers there, clears that workspace's storage and tells the user; its panels from other workspaces keep theirs. The host checks once a second from the moment a panel starts, whether or not its page ever finishes loading, so a module can go past the limit by whatever it writes in about a second before this happens. Its panels start again after the first clearing; if it goes over again within 10 minutes, they stay stopped until the user reloads them, opens the workspace again or restarts Tavora. |

## Grants

A module lists what it needs in its [manifest](../reference/manifest.md). Nothing is granted by the manifest alone:

- **The user is asked when they add a module.** Tavora draws the question itself, from the manifest as the main process read it, along with who made the module (Tavora, a publisher key or an unsigned folder). It shows in the new panel's place, and the module's page doesn't start until the user allows: there is nothing of the module running yet that could draw over the question or hide it. Cancel closes the panel. Preinstalled modules get no pre-approved grants. A connector the module lists in `permissions.onRequest` (only stream overlays) is asked for only right after a click in the module's panel that needs it, such as Copy OBS link. That question also shows in the panel's place, drawn by Tavora, while the module's page is hidden and paused (or in Tavora's own window when none of its panels is in view); until then the module runs without it. Closing the module's last panel ends the question as not allowed. An update that asks for more is still asked in Tavora's window, and the installed version keeps running with what it had.
- **The user grants exactly what they saw.** If an update asks for more while the dialog is open, it gets nothing it did not show.
- **Grants are kept by the host**, outside every module folder, for the module's publisher and id. Another publisher's module with the same id gets nothing, also when a development folder takes over the id: panels of the other copy that are open start again as the new copy, with its grants only, and so do panels that were closed then (in another workspace, or while Tavora was closed) once they open. They don't see the panel state or the tab content the other copy saved, and can't change or delete them: the other copy finds them again when the id comes back to it.
- **Revoking takes effect at once.** Settings > Modules > Website access lists every module allowed to reach websites, Settings > Connections every module allowed to use Discord (hidden while Discord is paused; the connection doesn't start then), AI usage, System info, Media or Leaderboards, every module allowed to read a folder (Folder access) and every module that asks to run while its game runs (Runs while its game runs, a switch per module, see [Running with the game](#running-with-the-game)), and Settings > Overlays & Streaming every module allowed to show stream overlays. Taking a grant back shows the workspaces the module is used in and removes its panels there; its data is kept. Data a module already received cannot be recalled.

### Network

`permissions.network` names exact hosts:

- HTTPS only, on the standard port, with lowercase public names. Wildcards, IP addresses, `localhost`, `.local` and `.internal` names are refused.
- The main process resolves the name itself and connects only when every address is public, so a granted name cannot be pointed at the user's PC or local network (DNS rebinding).
- Requests come from the main process, not from a browser session: no cookies, no browser sign-ins, no proxy credentials. A module cannot set `Cookie`, `Host`, `Origin`, `Referer`, `User-Agent`, `Proxy-*` or `Sec-*` headers, `Set-Cookie` is not passed back, and `Authorization` is dropped on a redirect to another host.
- An answer is read to at most 5 MB after unpacking. A request takes at most 15 s including redirects, with at most 5 redirects and 6 requests per panel at a time, counted across the panel's bridge ports.

A module can also ask to **read a program on this PC**, such as a game's local API, as `localhost:<port>` in `permissions.network`. The user grants it like a website, shown apart as "Read programs on this PC" with the port. Tavora only lets the module ask, never send: it can still read whatever that program shares, so the user should allow it only for a program they know. The rules:

- Exactly `localhost:<port>` with a port from 1024 to 65535, reached at `127.0.0.1` only (never what a name server or the hosts file says). No other address on the PC or the local network, no `[::1]`, no port ranges.
- `GET` and `HEAD` only, without method-override headers (`X-HTTP-Method-Override` and the like); anything else is refused before a request is made. Plain `http` is allowed here, and `https` with a certificate the program made itself, since nothing leaves the PC. Redirects are not followed.
- Never reachable: the ports Tavora listens on at that moment (stream overlays, page imports, Discord sign-in), and a fixed list of ports that hold control over the PC or a sign-in (Docker 2375/2376, Discord's local RPC 6463–6472, browser and Node debuggers 9222/9229). `network.readPage` and redirects from websites never reach a program on this PC.
- The other rules above (no cookies, the headers Tavora sets, the limits) hold the same.

A module page still cannot load remote code (`script-src 'self'`), even from a granted host, or run code from a string (`eval`, `new Function`, a worker made from a `blob:` address): workers start only from its own files (`worker-src 'self'`). It can't frame anything (`frame-src 'none'`), not even a page of its own origin, and every answer of its origin carries a policy: its own files get the module's, everything else (a missing file, a route's answer) one that runs nothing (`default-src 'none'; sandbox`). So no frame of its origin is a realm without the policy.

### Connectors

Connectors are capabilities built for one purpose. The host holds the connection, the sign-in and the token, and a module only reaches a fixed list of commands and answers.

- **Discord** (paused for now: Tavora doesn't connect to the Discord app or Discord's servers for it at all) shows and controls the user's own voice state through the Discord app on the same PC. A module sends only fixed commands with fixed fields, and never sees a token. Joining or leaving a channel, muting and unmuting need a real click in the module's panel. A granted module does see the user's voice channels, servers and who is in them, and the consent dialog says so. See [Known limits](#known-limits) for the named pipe it would use on Windows.
- **AI Usage** reads usage limits of AI subscriptions signed in on the PC. A module gets account names, plans and readings, never a login, a token or where it is stored. Each account is read at most once a minute for all modules together. Tavora doesn't look for AI accounts or read a login until a module that asks for this connector is installed.
- **System info** lets a module read this PC's hardware and how busy it is: processor, memory, graphics cards, drives and Tavora's own use, and how the connection is doing (pings to the router and one internet address), see [System info](#system-info).
- **Media** lets a module see what plays on this PC and play, pause or skip it, see [Media](#media).
- **Stream overlay** shows the module's overlay page in streaming software on the same PC, see [Stream overlays](#stream-overlays).
- **Leaderboards** keeps the module's leaderboards on Tavora's service with the user's Tavora account, once the user agrees in the module's panel, see [Leaderboards](#leaderboards).

## Remembered read-only files

A module can ask you to pick a file in Tavora's native file dialog after a real click, or several at once if the module asks for that. It receives a random reference and the file name for each, never the path. That choice lets the same publisher's module reread that exact file in that workspace, including after restarting Tavora, check whether it is still there (its size and when it last changed, without reading it), and, after another real click, have Tavora open its folder with the file selected. There is no write or folder-browsing call, and the module never learns the folder. Each read is limited to 50 MiB, with two reads at a time per module and workspace and four across Tavora.

Tavora remembers the last selected folder separately for each publisher, module and workspace. If that folder is unavailable, it may check the game's known save locations to start the native dialog there. These local hints are never given to modules and grant no access: you still choose each file yourself.

File access stays on this PC, outside backups and cloud copies. Restoring map data on another PC requires choosing the files again. A moved file or redirected link requires a new selection. Modules can forget a reference; clearing a workspace's or module's data also revokes its file access without deleting the selected files. Moving local module data to another publisher does not transfer file access.

## Folders on this PC

A module can ask to **read a folder on this PC**, such as the folder where a game keeps its replays or saves, in `permissions.folders`. Nothing is read until the user allows it. The Allow dialog shows the folder, the file types the module may read and the ones whose names it may only see, and says that it can't change anything. The rules:

- **Only where the manifest says, under three places.** A folder starts at the user's Documents or Saved Games folder and names the folders below it (`Documents/My Game`), or at `AppData\LocalLow` (Tavora 0.24.44 and newer), where many games (most made with Unity) keep their settings and saves. There it names at least a company and a game folder (`AppData/LocalLow/Company/Game`), so a module can never ask for all of LocalLow or a whole company's folder, and folders of Windows, browsers and runtimes there (`Microsoft`, `Sun`, `Oracle`, `Adobe`, `Google`, `Mozilla`, `Intel`, `NVIDIA`, `AMD`, `Apple`, `Apple Computer`, `Temp` and WebView2's `webviewdata`, in any case) are never allowed. LocalLow is where Windows lets low-trust programs write, mostly games. The rest of AppData (`Local` and `Roaming`), which holds other programs' sign-ins, is never allowed, also not through a link or junction inside LocalLow: Tavora checks where a folder really is. A drive, the user's own folder and the folders above it, Tavora's data folder and Tavora's own folders on the PC (`Documents\Tavora`, where key files, module zips and every module's saved files go, `Pictures\Tavora`, `Downloads\Tavora`, the module files folder and the cloud copy's folder), with anything in them or holding them, are never allowed.
- **If it isn't there, the user shows Tavora where it is.** `folders.choose` (after a real click, or Change folder… in Settings > Connections > Folder access) opens the system's folder dialog. A pick can't take in more than a manifest could name: besides the places above, Tavora refuses the known folders themselves and any folder holding them (Documents, Saved Games, AppData\LocalLow, Desktop, Downloads, Pictures, OneDrive...), dot-folders in the user's folder (`.ssh`, `.aws`...), other users' folders, ProgramData, Windows and network paths. A pick follows the same rules whatever root the manifest entry names: in LocalLow only a game's folder, never a system folder there, and never a browser profile. The module only hears whether a folder was chosen, never which.
- **Never a browser's sign-ins.** A browser or WebView2 profile keeps sign-in tokens and cookies in plain files. Under any root, Tavora never lists, reads or reports anything in a folder named `EBWebView`, `Local Storage`, `Session Storage`, `IndexedDB`, `User Data`, `Network` or `Cookies` (in any case), or in a folder that holds a file named `Local State`: such a folder counts as not there. A manifest folder or a pick that is one, or lies in one, is refused.
- **Read only, and only the file types it names.** The module can list the folder and its subfolders (up to 8 deep, at most 20,000 files), read files of the extensions in `read` (at most 50 MB each) and see files of the extensions in `names` by name only. It never sees other files, and nothing it can call writes, renames or deletes. Shortcuts (`.lnk`, `.url`) may only be names, since their content holds paths of the PC. Key and certificate files (`.pem`, `.key`, `.p12`, `.pfx`, `.ppk`) are never read, wherever they are: a manifest that lists one in `read` is refused (they can be listed in `names`). A manifest that asks for `Documents/Tavora` or a folder below it is refused too.
- **Never outside the folder, never where it is.** Paths are inside the folder, joined by `/`; `..`, drives, backslashes and names Windows keeps for devices are refused. Links and junctions are left out of listings, and a read is refused unless its real place is exactly the file named, so a link or a Windows short name (`PASSWO~1.TXT`) can't stand for another file or type, and a file with more than one name (a hard link) is not read; a refused read looks the same as a missing file. The module never learns where the folder is on the PC.
- **Showing a file in Explorer.** `folders.showInFolder` (after a real click, see [Calls that need a click](#calls-that-need-a-click)) selects a file the module may see in the folder in Explorer, or the folder it was in when the file is gone. It only selects; it opens and launches nothing and tells the module nothing, whether or not anything was shown.
- **Changes while a panel is open.** With `folders.watch`, a panel hears about files of its types being added, changed or removed while it is open; closing it ends that, and taking the grant back ends it at the next change at the latest.
- **Kept on this PC.** A chosen folder is kept for the publisher and module, outside backups and cloud copies; on another PC the user allows the folder again. Removing the module's data forgets it. The grant is checked again on every call, and an update that asks for another folder or another file type asks the user again.

A module can still read everything of its types in that folder, including files the user didn't mean for it, so allow it only for a module you trust with that folder. Data it already read cannot be recalled.

## Running with the game

A panel type may ask to run while one of its module's games runs (the manifest's `withGame`), so a module can keep track of a game, such as recording runs from its save folder, without a panel open. What the host guarantees:

- **Only after the user's yes, for the games it was given for.** It is asked in the consent dialog with the module's other permissions, drawn by Tavora ("Run while 9 Kings runs", with one line why), when the module is added or an update first brings it, and granted only when that dialog showed it. The yes is kept with the module's grants, for its publisher and id, and for the games the module named then: a version made for another game asks again before it runs with any. A version that drops `withGame` forgets the answer, so one that brings it back asks again, whether it comes from the catalog, a zip or a development folder. Settings > Connections > Runs while its game runs has a switch per module; off takes effect at once (the panel stops) and is kept as an answer, so the module doesn't ask again until a version newly brings it. Taking back all of a module's grants takes this too. Tavora's built-in modules can't ask for it.
- **Only while its game runs, in that game's workspace.** Only a game in the user's library counts (a game workspace; with several for one game, the one opened last), and only a module made for that game (its `games` names it; a module for any game can't ask). The panel starts when Tavora sees the game, also when it ran already as Tavora started, and goes when it closes. Tavora looks at the running programs for this even with game start and overlays off, but only while some module is allowed to.
- **One panel, the module's own.** It is the workspace's panel of that type when its layout has one, else a hidden panel that is never placed in the layout. It runs as any panel of the module in that workspace: the same session, data and grants (G1 to G11 hold), and nothing more.
- **Nothing that needs the user.** While it runs only for the game (the hidden panel, or a panel of a workspace not shown), every call that needs a click or key press, opens a dialog, menu, picker, tooltip, link, another panel or the hotkey dialog fails with `PERMISSION_DENIED`, and nobody is told. So do the save, open and clipboard addresses its session answers (`pictures.save`, `files.saveJson`, `files.openJson`, `files.save`, `files.open`, `files.exportJson`, the clipboard): Tavora tells its page's requests from those of the module's other pages, so it can't use a click made in a panel of the same module the user sees.
- **Always named, never shown.** Nothing is drawn over the game. Whenever a module runs with a game, the running game's card in Tavora's rail names it in one quiet line, for every game it runs with: also with "When a game starts" off and while the game's workspace is open (then the card shows only that line).
- **A crash starts it once more.** So does a page that stays unresponsive for 10 seconds (it is ended first). A second time in the same game session leaves the module off for that game until the game starts again, without a message. Tavora's own stops (clearing the module's storage when it grew too big, the user's Stop) are no crash: clearing holds the panel and starts it again after.

## Calls that need a click

Some calls change something outside the module's panel. They work only within 2 seconds of a real click or key press in that panel; a script cannot fake one, a held key is one press however long it repeats, a modifier alone (Ctrl, Shift, Alt, Win) is none, and each press allows one call, whether the module makes it through the bridge or through an address Tavora answers for the panel (the clipboard, pictures and files).

One exception: the click that adds a panel carries over to it once. A panel the user just added (its launch reason is `add`) may call `panel.openDialog()` once without a press, within 10 seconds of its page starting, to show a welcome. It doesn't apply over the game, after a restore or reload, or to a panel another panel opened with `panels.open` or `panels.openMany`, and nothing else gets it. One click gives one such dialog: when Add all or a layout adds several panels, only the last one added gets it.

- **`files.pickReadOnly`** opens a native file picker; one press opens it once. It may start next to a file the module already linked (`near`), but the module never learns that folder and gets no access from it. Only the files you select can be remembered, reread through `files.read` and checked through `files.check`. `files.forget` revokes that reference.
- **`folders.choose`** opens the system's folder dialog so the user can show Tavora where one of the module's allowed folders is. One press opens it once; see [Folders on this PC](#folders-on-this-pc).
- **`folders.showInFolder`** opens Explorer with a file of one of the module's allowed folders selected, or the folder it was in when the file is gone (selected in its own folder); one press opens one window. It shows only files the module may already see in that folder (the types its manifest lists), by the same path checks as a listing, and the module learns nothing back, not even where the folder is or whether anything was shown.
- **`files.showInFolder`** opens the folder of a file the module linked, in Explorer, with the file selected; one press opens one folder. It works only for a file that is still the one you picked, and the module learns nothing back.
- **`links.open`** opens an `http` or `https` address in Tavora's Browser panel, or, after the user confirms, in the system browser. The module learns nothing back. Addresses on the user's PC or local network (loopback, private and link-local addresses, local name endings and router names) are refused, and so are such links on a catalog listing (homepage, support link, readme) or from a developer's contact link.
- **`clipboard.writeImage`** puts a checked PNG on the clipboard. There is no call to read the clipboard.
- **`pictures.save`** writes a checked PNG where the user picks in Tavora's save dialog, which opens in the folder they last saved a picture to (at first `Pictures\Tavora`). The module only suggests a name, which Tavora cleans; it cannot pick the folder or file type, replace a file unless the user confirms it in the dialog, or read anything back, and it never learns where the file went.
- **`files.saveJson` and `files.openJson`** save and open a JSON file through Tavora's own save and open dialogs, which start in the folder you last used for that module (at first `Documents\Tavora`). The module only suggests a name, which Tavora cleans, and gets back the file name (and, for open, the parsed content of the one file you picked). It never gets a path, cannot pick a file or folder, and cannot replace a file unless you confirm it in the dialog. Each needs a real click or key press and works once per press; files are at most 8 MiB.
- **`files.save` and `files.open`** do the same for a `.csv` or `.xlsx` file, with the same dialogs, remembered folder and rules, and nothing else: only those two extensions can be chosen, a CSV must be UTF-8 text and a workbook a zip archive, and a file you pick with another extension is refused. The module gets back the file name, and for open the file's content (at most 8 MiB); never a path. Each needs a real click or key press and works once per press.
- **`ui.showMenu`** shows a menu that Tavora draws above every panel, so it can lie outside the module's panel. Tavora checks the menu first and draws only plain text, separators, headings, check marks and colour dots from plain CSS colour values (nothing that loads or runs), in its own style. One menu shows at a time, it closes with Esc, a click elsewhere or a workspace switch, and the module learns only which of its own items the user chose, or that none was.
- **`overlay.copyLink`** puts the link of one of the module's own overlays on the clipboard, and nothing else. There is no call to read the clipboard.
- **`overlay.showOverGame`** adds one of the module's own overlays to the user's game overlays, see [Game overlays](#game-overlays). One press adds one, and the user can turn all game overlays off.
- **`overlay.preview`** opens a preview window of one of the module's own overlays, see [Overlay previews](#overlay-previews). One click opens one window.
- **`overlay.openPage`** shows Tavora's Overlay page in place of the workspace and closes the panel's own dialog, as the user would by opening the page themselves. It takes no key and no data and tells the module nothing; the page is Tavora's own, so the module reaches nothing new on it. One click changes the screen once.
- **`hotkeys.set`** opens Tavora's own hotkey dialog. The module names the action and the target; the user picks the key, or cancels.
- **`panels.open`** opens, brings forward or switches a panel of the same module, in the workspace shown now, so it changes the workspace outside the module's panel. A module can open only its own panel types, never another module's panels, and one press opens or switches one panel. The panel asked to switch is the module's own page and may refuse; then nothing changes, and only the user can open the content in a new panel. The module learns only what Tavora did: shown, switched, opened or failed.
- **`panels.openMany`** opens several of the module's own panel types from one press, each type at most once and without content, in the workspace shown now. New panels go only into the area of the panel that was pressed: they split its dock group (as the manifest's `panelLayout` says) or open as tabs there, or, without a layout, where `panels.open` would put them. Panels of other modules never move, and a type that is open already only comes to the front where it is. The module learns only, for each type, whether it opened, was shown or failed.
- **`leaderboards.show`** shows Tavora's own question in the module's panel, see [Leaderboards](#leaderboards); one press asks once. **`leaderboards.hide`** takes the user off the module's boards and deletes their results there, so a page can't do that on its own either.
- **`panel.openDialog()`** shows the module's own panel big in a dialog centred over the workspace, inside it and above the other panels, which pause underneath; the rail and the header stay in sight, dimmed and not clickable. Tavora draws the frame around it: the module's name and icon and a close button, which the module can't cover or change. The module can set the title text next to the icon (`panel.setDialogTitle`, plain text of at most 200 characters, only while its dialog is open) to name what its settings are about; the icon, the close button and the rest of the frame stay Tavora's. One press opens it once; a panel just added may open it once on its own (see above). Pressed in a panel over the game, it closes the in-game layer, brings Tavora to the front on the panel's workspace and opens the dialog there, as if the user had come back and pressed it; the game window gets nothing. The user can always close it with the close button, and one a press opened also with a click beside it; the one a just-added panel opened on its own doesn't close on a click beside it, so a welcome isn't lost to a stray click. Closing needs no press. It is the same page in a bigger place, so the module reaches nothing new: no other panel, no window of its own, no fullscreen. The module learns only whether its dialog is open.
- **`panel.setMaximized(true)`** makes the module's own panel fill the workspace, as Maximize in its menu does, so it covers the other panels and they pause. It never reaches past the workspace: not the rest of the window, not fullscreen, not a new window. One press maximizes once. Putting the panel back needs no press, and the user can always do it with Restore in the panel's menu. The module learns only whether its own panel fills the workspace.

A module can still label a button misleadingly and get the user to click it. The result is the same as a link on any web page: the user sees the new tab, and the Browser panel is sandboxed.

A module can name its panel content without a click: **`panel.setContent`** names what the panel shows, and Tavora shows that name when the user hovers the panel's own tab. Tavora checks it first and shows only one line of plain text, at most 200 characters, below the panel's and the module's names, on that tab and nowhere else. The module learns nothing back.

A module's **patch notes** also show outside its panel, in Settings > Modules. They come from the changelog file in its package, not from the running page. Tavora reads at most 64 KB, checks the file first and shows only plain text lines (never HTML, Markdown or links), only for versions up to the installed one, and only when the user opens them.

## System info

A module granted the `system-info` connector can read this PC's hardware and how busy it is: processor, memory, graphics cards, drives and Tavora's own use, and how its connection is doing. The consent dialog says so. Two things run on their own terms: reading the PC, and watching the connection.

**Reading the PC**

- **Read only while a panel shows it.** Tavora reads the PC's performance only while at least one panel that is shown watches something. A hidden, minimized or covered panel counts for nothing, and with no watching panel there is no timer and no open counter. All panels share one reader, which looks at most once a second.
- **Windows' own numbers, read in Tavora's process.** The values are the performance counters Task Manager shows, plus the drive list and the names of the graphics cards. For NVIDIA cards, usage, video memory, temperature, clock speed and power come from NVIDIA's own library that ships with the driver (`nvml.dll`), loaded and read inside Tavora's process. Tavora starts no helper program and installs no driver; none of this is sent anywhere.
- **Numbers and names only.** A module gets the processor and graphics card names, sizes, percentages and drive letters with their labels. It never gets a file name, a path, a serial number, a user name or what other programs are running.
- **The list of apps is only for Tavora's own System Monitor.** Its Memory card can show the apps running on the PC with their memory and CPU (`systemInfo.apps`). Tavora answers that only for its own System Monitor, never for another module, with the grant or without. The list holds each program's file name and numbers, never a path, a window title or anything from inside a program. Tavora reads it with one call into Windows that opens no process, so a game and its anti-cheat are never touched, and only while the apps dialog is open and the panel is shown. It can't close or change any program.
- **Your traffic is only for Tavora's own System Monitor.** Its Connection section can show how much this PC downloaded and uploaded this week and in the last months (`systemInfo.traffic`), when the user turns it on. Tavora answers that only for its own System Monitor, never for another module. The numbers are totals from Windows' own record (Settings > Network > Data usage): no network names, no apps and nothing about what was sent. Tavora reads them only when asked, needs no admin rights, and keeps each finished month's totals in its data folder on this PC.
- **Network drives are not asked.** A network drive that doesn't answer could hold Tavora up, so its name and size are left out.

**Watching the connection**

- **It runs without a panel.** While Tavora's own System Monitor is in any workspace and the user has granted it System info, Tavora watches the connection, whether or not a panel is shown, so drops are logged. Without the module in a workspace, or without the grant (taking it back stops the watcher at once), or with it switched off, nothing runs. This is the one part of System info that does not wait for a panel.
- **Two pings every 5 seconds.** Tavora sends one ICMP echo (a ping with 32 bytes of filler) to the router and one to an address on the internet, `1.1.1.1` unless the user picks another. The router is the next hop of Windows' route to the internet, which Tavora reads from the routing table. The pings use Windows' own ping function inside Tavora's process: no `ping.exe`, no helper program, no admin rights. Nothing else is sent, nothing goes to a Tavora server, and no module sees the pings or the router's address.
- **Name lookups.** When the address is a name, Tavora asks the PC's name server for it, at most every 5 minutes (every 30 seconds while it can't be found), one lookup at a time. The address that comes back must be public; if it is not, Tavora does not ping it.
- **Only public addresses.** The address is a public IPv4 address or a name with a dot in it. Tavora refuses private, loopback, link-local, shared (CGNAT), documentation, multicast and other reserved addresses, names without a dot, local endings such as `.local`, `.lan` or `.home.arpa`, and router names such as `fritz.box`. Tavora's pings can't be aimed at this PC or the local network except for the router itself.
- **Only the System Monitor, only after a click.** Any granted module can read the log of drops, the settings and the readings. Changing the settings (watching on or off, the address) and clearing the log are only for Tavora's own System Monitor (publisher `official`, id `tavora.system-monitor`, which other publishers can't take), and each call must come right after a click or key press in its page, one per click. A change can be made once every 5 seconds, and a new address waits for the next normal ping.
- **The log of drops stays on the PC.** Tavora keeps the start, end and kind of each drop for 30 days in `connection.json` in its data folder, and a module can only read or clear it. The alert is a notice in the panel: no sound, no system notification. The same calls read whether Windows thinks it is online and the byte counters of the network adapter in use, which stay on the PC.

**Ending**

- **The snapshots end with the panel and the grant.** Closing the panel ends its watch at once. Taking the connector back removes the module's panels (see Revoking above) and stops the watcher, and a snapshot or an event is never sent to a module without the grant.

## Media

A module granted the `media` connector can see what plays on this PC, as Windows' media controls (the volume flyout) show it, and ask an app to play, pause, skip to the next or go back. The consent dialog says so.

- **Every app that plays, not one.** A module sees every app that tells Windows what it plays, such as Spotify, a video player or a browser tab, with the app's name, the title, artist and album, whether it plays, where it is in the song and a small cover. A browser tab's title can be the page's title. It never sees a file name, a path, a web address or other programs that don't play anything.
- **A helper program of Tavora's own.** Windows tells this only to programs that use its media API, so Tavora starts a small program that ships with it (`tavora-media.exe`). It reads Windows' media sessions and nothing else, waits for Windows to tell it about a change instead of checking over and over, talks only to Tavora through its own input and output, and uses no network. It runs only while a panel of a granted module watches and ends a minute after the last one stops, and when Tavora quits. If it stops by itself, Tavora starts it again up to three times in five minutes, then gives up until a panel starts watching again; Tavora keeps running either way.
- **Controls need a press.** Play/pause, next and previous work only within 2 seconds of a real click or key press in the module's panel, or a press of one of the module's own [hotkeys](#hotkeys), and one press allows one control. A module can't pause or skip the user's music on its own, such as when a game starts. The app decides whether it follows; Tavora sends nothing else to it.
- **It keeps coming while the panel is hidden.** Unlike System info, changes reach a watching panel also while it is hidden, so its overlay over the game or on stream stays current. They come only when something changes, never on a timer.
- **It ends with the panel and with the grant.** Closing the panel ends its watch at once. Taking the connector back removes the module's panels (see Revoking above), and a change is never sent to a module without the grant.
- **Windows only.** On other systems the connector says it isn't available, and nothing runs.

## Stream overlays

A module granted the `stream-overlay` connector can have Tavora serve its overlay page to streaming software such as OBS, which shows it as a Browser Source. This is the only way a module page is reachable from outside Tavora. The connector is what lets the module copy and reset a link. `overlay.publish` and `overlay.remove` only set what an overlay shows, which a link or a [game overlay](#game-overlays) then displays, so they need no grant. Without the connector Tavora keeps a published state only for a key that has a game overlay; for any other key, also one whose OBS link was made before the grant was taken back, the call succeeds and stores nothing, so a module can't fill the disk or keep feeding a link it lost. A published state can't be reached from outside Tavora without the connector.

- **Off until the user turns it on** in Settings > Overlays & Streaming. Tavora then listens on `127.0.0.1` only, on one port the user can change, so nothing on the network can reach it.
- **Only the links the user copies work.** Each overlay has a random link (128 bits), made by Tavora. Anything that asks without one gets nothing. The user can give every overlay a new link at once, and the old ones stop working.
- **Web pages can't reach it**, not even ones that point their own name at `127.0.0.1` (DNS rebinding): Tavora answers only requests addressed to `127.0.0.1` or `localhost` at its port, or to a link's own name (below), which browsers keep on this PC.
- **The page is locked down like a panel.** Tavora serves only files from the module's package (the same path checks as G6), only for `GET`, with a policy that loads no code from anywhere else and lets the page fetch from and connect to its own address only. It has no bridge: it can only read what the module published for that overlay, at most 16 KB of plain JSON.
- **In OBS the page can't leave.** OBS's browser lets Tavora hook nothing, so the link OBS loads leads to a page of Tavora's own with nothing in it but the module's page, in a sandboxed frame. The module's page can't navigate OBS's page, open windows, send forms, show dialogs or download, and the frame page's policy lets the frame show the module page's own address only, so the page can't take the frame anywhere else either, not even with a refresh. The link only redirects to that frame page, which has an address of its own (`f<link token>.localhost` at Tavora's port) where no module's page has ever run, and only that address may show the module's page in a frame. Tavora serves the module's page as a document only with a key the frame page gives its frame, a new one each time the frame page loads, good for 30 seconds and at most 10 loads (so the page can reload itself or move within its frame shortly after it starts). A service worker that a page could leave at the link's address under a Tavora before 0.24.105 sees only the link's redirect, never a key, so it can't show the page outside the frame. A page an older Tavora served at the link itself gets nothing more after the update (no state, no font) until OBS reloads the source, and every answer at the link's address asks the browser to clear what such a page left there. The frame shows a document only if it carries the page's policy (CSP Embedded Enforcement). The page can't start workers, and Tavora serves no worker script, so no service worker can answer the page's address with a document of its own later. Each link's page has an address of its own (`<link token>.localhost` at Tavora's port), so the pages of different links share no storage, and none can reach into the frame page around it. The frame page runs one script of Tavora's own, which gives the frame its address, takes on the colour scheme the page reports (so a dark page stays see-through), and passes on the Browser Source's Custom CSS that OBS puts into the frame page to the module's page, as OBS used to give it to the page itself. The frame page allows inline styles only for that CSS; it holds nothing a style could read. WebRTC is the one thing Tavora can't turn off there, as it does for every overlay page it shows itself (see [Known limits](#known-limits)).
- **Tavora's own font comes along.** Besides the module's files, every overlay server (the Stream overlays one and the game overlay and preview pages) serves one file of Tavora's own, `_font.css`: the interface font the user picked, embedded, so overlay pages match the app. Every `_state` message also carries that font's id, so the page can swap it when the user picks another one. Neither holds anything from a module.
- **A link works only for its module.** It belongs to one module, under its publisher, in one workspace. When the module is removed, replaced by another publisher's module with the same id, or loses the grant, the link stops working and open overlay pages are cut off at once; OBS gets nothing more from that link.
- **What an overlay shows goes on stream.** Whatever the module publishes for it is visible to viewers. The consent dialog says what the connector does; a module still decides what it shows.

## Game overlays

Tavora can show two kinds of things over the user's game, and with the Everywhere setup over any other program too: a module's **overlay page**, and **panels in game**. Neither is the connector above, and neither reaches anything outside Tavora: they are windows of Tavora's own on the user's screen.

- **Off until the user turns it on** in Settings > Overlays & Streaming. While it is off, the calls only open that setting. Turning it off closes every window at once. The Live button in the workspace header pauses overlays: it closes everything until the user shows it again or Tavora starts again (it is not remembered).
- **Only the user's own overlays, where the user put them.** Overlays and panels in game are kept in **setups**: **Everywhere**, **All games**, and one for each game workspace that has one, each with at most 8 items. What shows is Everywhere, plus either the setup of the library game in front or, when that game has none, All games; a game's setup and All games never show together. The game in front is found by reading which program owns the window in front (the same look the game watcher takes, with the same limited access).
- **Everywhere shows outside games.** Its items show over any program and over the desktop, on the main screen, whether a game runs or not. They hide only while one of Tavora's own windows is in front. A module can't put anything there (see below); only the user does.
- **Over a game, only while it is in front.** The items of a game's setup or of All games hide within a moment (up to about 0.4 seconds) after another window comes to the front, Tavora included, and an overlay window that stays out of the front is closed after about 30 seconds. With **Keep overlays on the game when you alt-tab** on in Settings > Overlays & Streaming (the default), they instead stay on the game window the user left, while it is still open and not minimized: right above it in Windows' order of windows, so any window over the game covers them too (a game that is itself always on top keeps them on top); Tavora checks that window (the same window handle, owned by the same process) each moment and hides them once it is gone. The layer and the overlay keys work only while something shows, and over a game only while it is in front.
- **Where an item may go follows where it was made.** Something made in a game workspace (a module overlay or a panel) goes only into that game's setup. A module overlay made in a personal workspace lands in All games; a panel from a personal workspace may go into any setup. `overlay.showOverGame` never chooses: it puts the overlay in its game's setup (made for it when there is none) or in All games, never in Everywhere, and it is refused when that setup already has 8 items. The user removes items on the Overlay page (see below), and removing the module (a development folder's too), a workspace (its setup goes with it), or a module replaced by another publisher's with the same id removes them from every setup. A module can bring a removed overlay back only with a new click in its panel while Game overlays are on.
- **Nothing is put into the game.** Tavora does not inject code, read the game's memory, hook its graphics or keyboard, or draw into its window. The overlays are ordinary windows above it. The only calls to Windows are reading which window is in front, where its client area is and whether Windows thinks a full-screen game owns the screen, asking for the path of the program that owns it (the game's process is opened with the limited query right only, never with rights to read its memory or change it), and, after the user closes the layer, giving the game the focus back.
- **Windows never outlive Tavora.** They close when Tavora quits, when its main window closes, when it gets a stop signal and when its process exits. A development restart ends the old process and its windows before the new one starts.
- **The page is locked down like a Stream overlay page.** It has no bridge, loads only files from the module's package (the same path checks as G6) from a Tavora-internal address, under the same policy, and can reach nothing else. WebRTC goes only through a proxy that does not exist, as in a panel, so no UDP leaves either. It can only read what the module published for that overlay, at most 16 KB of plain JSON. It needs neither the Stream overlays server nor the connector.
- **Capture hiding is opt-in.** By default the windows show in screen capture and recording like any other window. The user can turn on Hide from capture per overlay, which excludes it from capture. It is off by default because some anti-cheats flag windows that are hidden from capture over a game.

### Overlays

An overlay page can't take input: it is transparent to the mouse, never takes the keyboard, and is always there (or toggled by a key the user set), as the user chose. The key that toggles an overlay is set in Tavora's hotkey dialog, is one key for the overlay in every setup it is in, and works only while a setup with it shows. The module never learns it. A module's keys for overlay pages can't start with `panel-`, which Tavora keeps for itself; `overlay.showOverGame` refuses them. `overlay.hideOverGame` and `overlay.overGame` only remove or list the module's own overlays of the panel's workspace (from every setup they are in), and need neither a click nor a permission. `overlay.setSources` lets a panel name what it can show (at most 64 entries, each a key, a name and a size, checked and kept in memory only). Tavora draws the names as plain text on the Overlay page, and an entry adds an overlay only when the user clicks it there, which is the same overlay `overlay.showOverGame` would add, in the setup the user is arranging and under the same limits. The page then tells the panel (`overlay.onOverGameChange`) so it can publish the new overlay's state. An entry that says `grows` makes the size it lists that overlay's frame size, times the scale the user dragged it to, also later: the panel can make its own frame bigger or smaller by listing another size, at most 4000 pixels of a 1080 px high window each way times that scale, and never past the game window (the frame is placed inside it as always). It stays click-through and in the place the user gave it, and a frame of an entry without `grows` keeps the size the user set. The user's Settings press on a frame puts the panel in its dialog over the Overlay page and hands it the key of the overlay (`panel.onOpenSettings`); a module reaches nothing it could not reach from its own panel.

### The in-game layer

The user has **one** key for it ("Tavora over game", set in Settings > Overlays & Streaming with the hotkey dialog). It works whenever something shows: over the library game in front, or over the main screen when only Everywhere shows. While the user holds the layer open:

- **A veil** covers the game's window (or the main screen, when the layer opens over no game): a Tavora window, black at about 30 % opacity, that takes clicks and does nothing with them, so the game isn't played by accident. It never takes the keyboard. It is one small page of Tavora's own (no files, no network, no bridge) that paints the dark sheet only while Tavora's main process keeps telling it so, twice a second; with nothing heard for 2 seconds it turns fully transparent, and if the page itself stops it makes the window click-through. It stops mouse clicks the way a window does: a game that reads the mouse straight from the device (raw input) may still see them. And if Tavora's main process hangs altogether, Windows alone decides what a click on its unresponsive window does; the veil can only become invisible then. Closing Tavora, or the game window going away or being minimized, ends it.
- **Tavora's card** sits at the top of the layer: Use or Arrange, and Close. It is a page of Tavora's own UI (served from Tavora's address, in the host's session, with no bridge and nothing a module gave), in a window of its own that lets clicks through except over the card. It takes the keyboard only when the user clicks or tabs into it, and is visible to screen capture like the veil.
- **In Use**, where the layer always opens, panels in game show on top of the veil and take the mouse and the keyboard; overlays stay click-through, and nothing has a frame.
- **In Arrange**, every overlay and panel shown gets a frame Tavora draws (the page is below it), so the user can move, resize or close it, or open the Overlay page with a small button on the frame. The button only opens Tavora's own page and closes nothing. The frame lies over a panel too, so the panel takes no clicks or keys then.

The keys are taken only while something shows, and then they can't be used for anything else: while Everywhere has items, the layer key and the toggle keys of Everywhere's items are taken in **every** program in front except Tavora's own windows; while All games has items, the layer key and the toggle keys of All games' items are taken in every library game without a setup of its own. Tavora's hotkey dialog refuses a key that collides with another one that works at the same time. A panel from a personal workspace learns when the layer opens and closes and the size of the area it is in (the usual `workspace.resize`), not which game or program is in front. The layer opens only over the window that was in front when the key was pressed (or over the main screen when that was no game), and not over a game that owns the screen exclusively (Tavora says so instead). The key again, or Esc, closes it: panels return to their workspace slots, overlays are click-through again, and the game gets the focus back. While the layer is open Tavora takes Esc globally, so the game doesn't get Esc until it is closed. Nothing else from Tavora is shown over the game. Use or Arrange is kept in memory only; the layer opens in Use each time. If the window it opened over leaves the front, or Tavora's own window comes to the front of a layer over the screen, the layer closes.

### Panels in game

A panel type can set `inGame: true` in the manifest. Only for those types, the panel's own menu offers **Show in game** (and **Stop showing in game**). That click is the consent: no module call is involved and a module can't ask for it. Panels of other types get no such item.

- **Only while the user holds the layer open.** A panel in game is *not* over the game normally. It is over the game only while the layer is open, and it goes back into its workspace slot when the layer closes. The slot says "Open in game" meanwhile. What the user chose is kept across a restart by the panel's id; a panel that no longer exists is dropped.
- **The same panel, the same rights.** Tavora moves the panel's own view into the overlay window; it does not start a second copy. (If the panel's workspace is not the one shown, Tavora makes its view for the layer and closes it again afterwards.) The page keeps its bridge, session, storage, grants and identity, and what the module may call does not change. Nothing new can reach the page or leave it. The module can notice that it was moved, because the page is resized, paused and resumed like any panel whose place changes, but it is not told why.
- **Same limits as other overlays.** It counts toward the 8 items of each setup it is in and is off until Game overlays is on. One panel can be in several setups; it is still the one panel, with its own place and settings in each. Its place and size are kept per setup, relative to the game's window (the main screen in Everywhere) (anchored to its nearest corner or edge, in units of the window's height) and changed by dragging in the layer or on the Overlay page. The frame around it shows the panel's name and a close button that means Stop showing in game.
- **Calls that need Tavora's window are refused.** While a panel is in the layer it can't open a save or open dialog (`pictures.save`, `files.saveJson`, `files.openJson`, `files.save`, `files.open`, `files.pickReadOnly`), show a file in its folder (`files.showInFolder`), the hotkey dialog (`hotkeys.set`), a menu (`ui.showMenu`), the consent dialog or a setting (`overlay.copyLink` when it would need one, `overlay.showOverGame`), a preview window (`overlay.preview`), Tavora's Overlay page (`overlay.openPage`), another panel (`panels.open`), maximize it (`panel.setMaximized`) or open a link (`links.open`). They fail with `PERMISSION_DENIED`, and Tavora tells the user once per press: "Close the game layer to do this." Nothing waits for an answer that can't come. `links.open` also works only for the workspace shown now.
- **Input only in Use.** A click or key press counts as the user's (what links and files need) only while the layer is open in Use. In Arrange the frame covers the panel and nothing it reports counts; at any other time none is counted. Tavora's own shortcuts leave the keys to the panel. While a panel has the keyboard, Windows reports one of Tavora's own windows as the one in front; Tavora reads only that it is its own and keeps the game as the one in front.
- **It goes when the panel goes.** Closing the panel (which takes it out of every setup), removing its module or workspace, a module replaced by another publisher's, turning Game overlays off, closing Tavora's window or quitting closes the overlay window, and the user can't close it any other way (Alt+F4 is ignored; the layer closing is how it leaves). A panel that crashes shows its usual crash screen in its slot.

### Live views

A panel in game can also have a **live view**: while the layer is closed, Tavora shows the panel's module overlay page (the manifest's `overlay`) in the panel's spot over the game. It is the same kind of window as a game overlay, so everything under [Overlays](#overlays) holds: it is click-through, never takes the keyboard, has no bridge and no network, and shows only while a setup it is in shows and Game overlays are on.

- **`panel.setLive(state)`** sets what that page shows: plain JSON, at most 16 KB, kept in memory only and forgotten when the panel closes. It needs no click or permission, and it is what makes the live window appear over the game: for a panel the user already put in game (Show in game, which is the consent), the module decides when its page shows, by setting or clearing the state. The user can set per panel whether the view is always there or toggled by a key, its opacity and Hide from capture (off at first), or stop showing the panel in game.
- **It reaches nothing else.** The page can read only the state its own panel passed. A module without an overlay page gets no live view.

### Overlay page

The user arranges overlays and panels in game on the **Overlay page**, a page of Tavora's main window opened from the Overlay button in the workspace header, a panel's menu, or the small button on an overlay's frame in the in-game layer. (There is no separate window for it.) It shows the chosen setup's shape (the game's window, or the screen) as a canvas with a soft grid, and every overlay and panel in game of that setup where it sits, scaled. Every change is written at once and shows over the game.

- **Positions** stick to the nearest corner or edge of the game window and scale with its height, so a wider window adds room at the sides without stretching anything. The size of the game window last seen is kept for each game, on this PC, to draw the canvas. A position saved by an older Tavora stays as it was until the game's real window is seen, then it is converted once, to the same place on screen. A file written by a newer Tavora is copied aside before this one writes it, and read as far as this Tavora can. When Tavora first moved the file to setups it kept a copy of the old one among its backups (`backups/before-overlay-setups`); if that copy can't be made, it doesn't write the file until the next start. An older Tavora can't read the moved file and sets it aside.
- **The pages on the canvas are the real overlay pages**, served exactly like the game's overlay window: from a Tavora-internal address, with no bridge, no network, a session of their own and the same policy, reading the same state the module publishes. They cannot take the mouse or the keyboard: a layer of Tavora's own is over them. A panel in game whose module has an overlay page shows that page; any other panel shows a box with its name. The module can't tell the page from the game.
- **Each setup has its own places.** An item in several setups has its own position, size, mode, opacity and Hide from capture in each; its key is the same in all of them. An item in both Everywhere and the game-side setup shown shows once, as the game-side setup has it. Positions stay on this PC. Changes apply immediately; leaving the page (any workspace on the rail, or the lit Overlay button) takes its views away.
- **The page and its layer are Tavora's UI.** The page is the main window's own; the layer over the canvas is a second page of Tavora's own that can only read the theme and language, and send the messages the page checks (move, select, undo). The page lists every panel of every workspace, by name and workspace, so the user can add one to the setup shown; the list is host UI only, and no module sees it or learns that a panel was added, apart from the usual resize of its panel when it is moved into an overlay. Adding a panel takes the user's click, follows the rule above (a game workspace's panel goes only into its game's setup) and moves nothing beyond Tavora's own windows. The page can also add or remove a game's overlay setup (Add overlay / Remove overlay on the rail), and move an item of a personal workspace between Everywhere and All games.
- **The game picture is optional and the user's click makes it.** *Take picture* asks the OS for a window capture, the same one OBS's Window Capture uses (Electron's `desktopCapturer`). The OS can't be asked for one window alone, so it hands over a picture of every open window; Tavora looks only for the game's window, by the window handle it saw in front, keeps that one and discards the rest at once, unread. It first looks at the list of windows without any picture, and takes none when the game's window isn't open. Nothing is injected, hooked or read from the game, and nothing is captured unless the user clicks. *Choose picture…* uses Tavora's open dialog. The picture is kept as one PNG per setup (a game, Everywhere or All games) in Tavora's data folder, shown dimmed under the grid, never sent anywhere, and removed with *Remove picture* or with the game. *Take picture* works for a game's window only; Everywhere and All games take a picture from a file you choose, and Tavora never captures the screen for them. *Preview as* reads only the size of each connected monitor, to show its shape; nothing is saved.

### Overlay previews

A module with an overlay page can ask, after a real click in its panel, for `overlay.preview(key)`; The Overlay page and Settings > Overlays & Streaming have a Preview button per overlay and per OBS link. It opens a small, ordinary Tavora window (not on top, not click-through, in the taskbar) titled with the module's name, showing the overlay page at its real size on a dark, light or checkered background. It is served exactly like the game overlay page: from a Tavora-internal address, with no bridge, no network and the same policy, and it reads the same live state the module publishes. There is one window per overlay. It needs no permission and works whether Game overlays and Stream overlays are on or off, because it shows nothing over a game and serves nothing outside Tavora. To feed the preview, Tavora keeps an OBS link (a secret address) for the key, as it does for a game overlay; that link is still served on the network only while the module has the `stream-overlay` connector and Stream overlays is on, so a preview alone puts nothing on the network.

## Hotkeys

Modules can name actions in their manifest, and the user can bind a key to each in Tavora's own dialog. The module never learns the key, only which action fired for which of its targets. `hotkeys.list` and `hotkeys.remove` reach only these keys, never the keys the user set to toggle the module's overlays.

- **Only the user sets keys.** The dialog opens only right after a click in the module's panel, Tavora draws it and catches the key, and the module can't press it or choose for the user.
- **A key needs a modifier** (Ctrl, Alt or Win) unless it is an F-key or a number-pad key, so a hotkey never takes letters the user types with.
- **Keys work only while they're needed.** Tavora registers a workspace's hotkeys with the system only while that workspace is shown in Tavora and the module has a panel in its workspace, and lets them go otherwise. The game itself doesn't get a key that is a hotkey right then.
- **One key, one action per workspace.** Tavora refuses a key that is already a hotkey in the same workspace, or that another program holds. Settings > Overlays & Streaming lists every hotkey, in every workspace, and removes any of them.

## Module files

`blobs` keeps pictures, PDF files and sounds for a module, per workspace. `blobs.app` keeps them for the module across every workspace:

- The host picks every file name (a random 128-bit id). A module never names a path.
- Only PNG, JPEG, GIF and WebP pictures, PDF files and MP3, Ogg and WAV sounds are stored, judged by their first bytes. SVG and everything else is refused. Files are served with `nosniff` and a content security policy that runs nothing. A PDF is served as an attachment: Tavora never renders it as a page, and only the module that stored it reads it. A sound is only played or decoded by the module's own page.
- A module only ever reaches its own files: a workspace's files from that workspace's panels, and its files for every workspace from any of its panels. Never another module's, and never the files of the same id from another publisher.
- Limits are 50 MB per file and 500 MB per module and workspace, and 500 MB more per module for files shared by every workspace. A workspace's files are deleted along with the workspace; the shared ones with the module's data in Settings > Modules.
- Only the user can move the folder, in the system's own dialog. A module cannot trigger the move or learn the path.

## Installing modules

A zip is checked before anything is extracted:

1. The zip is read into memory, within the archive size cap, and its manifest is read and validated before anything else.
2. Only regular files are extracted. Links, absolute paths, `..`, drive letters, reserved Windows names and paths that differ only in case are refused.
3. The archive size, the unpacked size, the file count and the compression ratio are capped.
4. The signature is checked, and the publisher (a key, or `local` for an unsigned zip) is recorded by the host. Ids starting with `tavora.` are refused. A zip whose id is already installed is accepted only as an update signed by the same publisher, with a higher version.
5. Data is keyed by publisher and id. A module from another publisher that claims a removed module's id starts empty.
6. The module is unpacked into a temporary folder and moved into place, so a half-extracted module never loads.
7. Nothing from the archive is ever run.
8. At every start, and every time Tavora looks for modules again, the installed folder is checked against the publisher the host recorded: its files must still be exactly what that publisher's key signed. A folder that was changed, replaced or signed by another key doesn't load at all, so it never gets that publisher's data or permissions and writes no data of its own. Settings > Modules says so, its data stays, and a zip from the same publisher (the catalog's version, or one picked by hand, also the same version) repairs it. A folder put there by hand with no record loads as an unsigned `local` folder, as before. To keep starts quick, a check is kept with a stamp of the folder's files (names, sizes, change times and file ids) in Tavora's data folder, and a folder is hashed again only when the stamp changes. The check runs when modules are looked for, not on every file read: a file changed while Tavora runs is caught at the next start or look, and its panel's page may load it before then.

### From the catalog

The Catalog view of the module library lists modules from Tavora's catalog and installs them. The catalog is a new way for the app to reach the network, so it follows these rules:

- **The app asks, never a module or page.** The main process fetches the list and the zip; the host UI gets checked plain values, and modules and Browser pages cannot reach the catalog at all. It is asked only while Online features (Settings > Games) are on, with no cookies or referrer, and with your sign-in only when you rate, reply, report or write to a developer, and, while you are signed in, when you open a module's page (to show your own rating of it). It learns only which zip is downloaded, which module's page you open, that you installed a module from Browse or updated one from the catalog (its id, nothing about you), what you chose to report, and the ratings you post. The list is always the whole catalog, so it doesn't learn which game is open.
- **The server is not trusted.** Every listing is checked field by field, and its text is shown as plain text, never HTML or Markdown. The name shown after "by" is only the developer name the service gives for the publisher key, in the same plain name form as above.
- **Pictures are only pictures, the readme is only text, and the homepage is only a link.** A module's page shows the icon and screenshots its listing names. Tavora fetches a card's icon by its SHA-256 when the list shows it, and each screenshot only when you open the page, reads at most its listed size, checks the hash and that its first bytes are a PNG or WebP of at most 1 MB, (256 KB for an icon), and shows it as a plain picture, like a module icon. The service checks every screenshot and icon too before it lists them. The readme is read in the main process for its headings, paragraphs, lists, code, bold, italic and links only, and shown as plain text by the host UI (never as HTML): pictures and HTML are never loaded or run. A link in the readme shows its words and opens only when you click it, and only if its address is an `http` or `https` one that the module's current readme really contains: Tavora reads the readme again itself before opening it, so the page can't ask for any other address, and an address with another scheme is shown as plain words without a link. It opens in a Browser panel or where you pick, like the homepage. The homepage shows as plain text and opens only as an `http` or `https` address, like a module's link: in a Browser panel or where you pick. Tavora reads it from the listing again itself, never from the page that shows it. **The support link is only a button.** A module may name one `https` address or one email address as its `support` link. The page shows a Send feedback button, never the address as a link in the page, and nothing happens until you click it. Then Tavora reads the link again itself, from the module's own manifest or the catalog listing, and opens it only in these two forms: a web address like the homepage, in a Browser panel or where you pick, or an email address in your mail app as a plain `mailto:` link with just that address. Any other kind of address is refused, and a module can't pass an address of its own.
- **A zip is installed only if it is the listed one.** Tavora asks for the listing again itself, downloads the zip into memory with its listed size as a cap, and checks its SHA-256 against the listing before anything uses it. The zip then goes through every check of [Installing modules](#installing-modules), and must also be the listed module id and be signed by the listed publisher key, all before a file is written. An unsigned zip is refused.
- **A report needs a sign-in, and Tavora keeps who sent it only while it is open.** Report, in the catalog or in Settings > Modules, sends Tavora the module id, its publisher key and the SHA-256 of its zip (the installed one, for a module installed from the catalog), the reason you pick and an optional note, and only after you said yes. Tavora keeps your account with the report so it can answer you, and deletes it when the report is closed (dismissed, or the module is taken down) or you delete your account. The developer is told only that the module was reported, never who sent it. Reports are limited per connection and hide nothing by themselves: a person at Tavora looks at them and decides.
- **A rating is only what you post.** Rating a module needs a sign-in, and sends the stars, your review's text and the version you rate, nothing else about your PC or your other modules. The service keeps them with your account until you delete the rating or the account. Your review shows your profile name and picture; your profile stays private everywhere else. Reading reviews needs no sign-in. Reporting a review needs one and sends only its id; Tavora keeps who reported it only while the report is open.
- **Conversations are private and pseudonymous.** A user can write to the developer of a published module, and Tavora can write to an account; there are no other kinds, so nobody can message another user out of the blue. A conversation holds plain text of at most 2,000 characters (no files, and links, email addresses and slurs are refused), the versions of Tavora and the module on the first message, and nothing else about your PC. The developer sees you as "User · K7" (a label per conversation, so you can't be linked across modules), you see them as `Developer of <module> (<developer name>)`, and Tavora as "Tavora": your profile name, picture, email address and account id are never shown to the other side. Either side can block a conversation, which closes it for both, and report it. Tavora remembers a block (only your account and the module) so no new conversation about that module starts, even after the blocked one is deleted, until your account is deleted. Tavora reads only its own conversations and conversations someone reported; it can't read any other. An idle conversation closes after 30 days, a closed one is deleted after 180 days unless it is reported, and either side can delete it sooner. Deleting your account closes your conversations, removes the text of your messages and deletes your reports; icons you offered that still wait for review are deleted too. Email copies of new messages are optional (off by default for developers) and carry the text and the pseudonym only.
- **Installing grants nothing.** A module installed from the catalog asks for its network hosts and connectors when it is added, like any other.
- **A new version is checked before it lists, and a person decides when a check fails.** The service runs the automatic checks on every upload: the word filter (slurs and adult terms) over its texts, whether it asks for network or connectors or more than the version before, whether it copies another publisher's module (by name or by file hashes), warning signs in its scripts (`eval`, `new Function`, WebAssembly, code loaded from the internet, obfuscation; a short list of exact library pieces that only look like these is skipped) and a ClamAV virus scan. If every check passes, it lists at once. If any fails, **or cannot run**, the version waits: it isn't listed or handed out, and nothing approves it but a person at Tavora. The first module of an account that has never had a version approved, and any new or changed icon or screenshots, always wait. Tavora's own modules (`tavora.` ids, uploaded from Tavora's account) never wait: the checks still run and are kept for the review page. Declining deletes the zip, and a banned developer's account and keys can't publish and their modules leave the catalog. Their open conversations with users close ("Closed by Tavora"), their contact link is hidden, and they can't reply to reviews or change the link. Lifting a ban lists the modules again; closed conversations stay closed. These checks catch careless and obvious cases; they don't prove a module is safe. A module that passes still runs in the sandbox with only what you grant, and is checked again on your PC. The rules are in [What's not allowed in the catalog](./catalog-rules.md).
- **Discord and AI Usage took their data along, not their grants.** They used to ship with Tavora and now come from the catalog. At the first start without them, Tavora hands what they saved (settings, browser storage, their panels, overlays, stream links and hotkeys) to `wellbrained.discord` and `wellbrained.ai-usage` under the WellBrained publisher key, Tavora's own, and to no other key. Nothing installs by itself: their panels offer Install, and the installed module asks for its connectors like any other. Until then the data is listed in Settings > Modules, where you can delete it.
- **Updates come only from the same publisher, only forward, and never widen a module quietly.** While online features are on, Tavora downloads the whole catalog index (never a list of what you have installed) and compares it on your PC with the modules you installed from the catalog. An update is installed only if its zip passes every check above, including the safety lists, is signed by the same publisher key as the installed module (or its successor by a signed succession) and has a higher version; an older version, the same version or another key's zip is refused. Updates wait for you to press Update, unless you turned on **Update modules automatically** (off by default): then one that asks for nothing new installs at once and its panels reload. One that asks for network hosts or connectors the installed version did not always waits for your yes, with the setting on or off, and the installed version keeps running until then; allowing it grants exactly what the dialog showed. A module installed or replaced from a zip by hand is not updated from the catalog.

### Built-in modules from the catalog

Tavora's own modules (ids starting with `tavora.`) ship inside the app, and the app can also take a newer copy of one from the catalog, without a new app release. This is off until Tavora turns it on, and then it follows these rules:

- **Only Tavora's key counts.** A downloaded copy runs only when it is signed by Tavora's own publisher key, pinned in the app, or by a newer key that replaces it through a signed succession inside Tavora's own account. Any other key, an unsigned zip, a revoked key and a blocked zip are refused, and so is the Install from zip button for a `tavora.` id, as before. The catalog accepts such an upload only from Tavora's account, signed in, never with a publish token.
- **It must be a module that ships with the app, and newer.** Only an id the app itself ships can update, never one that moved to the catalog. The version must be higher than the shipped copy, than the copy running and than the newest version ever installed, so an older signed zip can't be put back. The module names the oldest Tavora it needs, and this Tavora must be new enough.
- **Checked again at every start.** The copy lives in a folder in Tavora's data folder. Before it runs, Tavora checks its files against the signature, that nothing was added, changed or swapped for a link, and the signer, the safety lists and the pins again. If anything fails, the copy that shipped with the app runs instead; it is never removed. A copy that is blocked, signed by a key that was revoked, no longer needed (the app now ships the same or a newer version) or no longer shipped is deleted. Its data stays where it was, and the shipped copy opens it.
- **Same rights, same questions.** A downloaded copy is Official, like the shipped one, and keeps its data. It gets no grant for free: what it asks for is granted the same way, and an update that asks for network hosts or connectors the earlier version did not always waits for your yes.
- **The folder is not backed up or copied to the cloud.** It can be downloaded again, and it only ever holds signed files.
- **Tavora's key stays with the maintainer.** These updates are signed and uploaded only from a development build of Tavora, never from the app you install. The key is a file the maintainer picks for each upload. With "Remember the key on this PC" it is kept sealed by the system (DPAPI on Windows) for that user on that PC only: never in backups, the cloud copy or the account's key vault. Forget key deletes it, and a saved key that is no longer Tavora's pinned key, or was revoked, is deleted when it would be used.

## The Add a game list

Tavora lists the games installed on your PC to order the Add a game picker. The main process reads them from what the launchers (Steam, Battle.net, Epic, GOG and Windows) keep on disk, and reads Steam's last-played times from its own files, read-only. Tavora also notes when it last saw each game running and uses the install date. The covers of the games played lately are Steam's own cover art from its library cache on your PC, read-only and never downloaded. This stays on your PC: it only orders the list, goes to Tavora's own window and nowhere else, is never sent to the Tavora service or any other address, and modules and Browser pages can't reach it. Two exceptions, each a game's name only after you act: when you add one of these games that Tavora's built-in list doesn't know (from Add a game, or with the Add button of a game that is running), its name goes to Tavora's game search (only while Online features are on), as if you had typed it, so it is added with the modules made for it; and when you press Ask for a module, below.

## Ask for a module

When a game has no modules, its empty page offers **Ask for a module for &lt;game&gt;**. It is one click and needs no account, and nothing is sent before you press it. The main process then makes one request to Tavora's service, only while Online features are on, with no cookies, referrer or sign-in:

- **What is sent:** the game's name, its Steam application id and Tavora's id for it when it has them, and a code. The code is made on your PC from a random number kept there and the game, so the service can count one vote per PC and game but can't tell which games came from the same PC, and it is not your account. Nothing else goes: not your other games, your modules or your address (the service doesn't keep addresses; it only uses it to limit how often one connection can ask, and to count one vote per network and game).
- **What is kept:** per game, its name and ids, how many votes it has and the day of the first and last vote; per vote, the code and 4 hex digits of a hash of the game and your network (the first three parts of an IPv4 address, the first three groups of an IPv6 one) under a secret kept on the server, so votes from one network count once. Without that secret the digits say nothing about your network, and even with it they match many networks, so they don't link your votes for different games. The private admin page lists the games by votes. Nothing is shared or sold, and a vote is never tied to an account.
- **Asking twice does nothing.** Pressing it again, or from the same PC on another day, doesn't add a vote. Tavora remembers on your PC that you asked, so the button turns into a thanks.
- **It never blocks the game.** The game is already added; if the service can't be reached, the button says so. The service is limited to 20 votes an hour per connection, and per network to 20 new games and 50 votes for games already asked for a day.

## The Browser panel

The Browser panel shows any website, so here the attacker is any page:

- A page cannot reach Node, Electron or the host. It has no preload and no bridge.
- Each workspace gets its own browser session, and a page cannot read module bundles. Only sites you sign in to for all workspaces open in the shared one, also when another site redirects there.
- A page moves to the other session only when you started the navigation (the address bar, a link you or a module opened in a new tab, Open) or right after a click or key press in the page; that navigation uses the click up. Tavora then loads the address itself, with the page's origin as the referrer, and the redirects of that load follow the same click: they may move it on to the other session again, at most 5 times. When a page goes there by itself, or a redirect takes such a navigation there, the panel shows that the page wants to open another site, with Open and Stay on this page. It opens the site only when you press Open, and while it asks, the page can't ask for another one or turn the question into an error to try again. When the panel reopens the page it showed last time (Tavora starts, a workspace opens again) or you press Reload, Back, Forward or Try again, the page may have chosen that address itself: it opens in the session it belongs in, as before, but a redirect from it to the other session asks first, and Try again on an address of the other session asks before it opens it. While the panel asks, a page the page behind it goes to in its own session doesn't end the question either, and changing which sites sign in for all workspaces (or block ads) leaves it in place too. When such a change moves the site of the page shown to the other session, the page goes along: an address you chose yourself (typed, Open, a link you opened in a new tab) opens again there, and any other page opens at its site's home, so an address a page or a redirect picked is never loaded there like one you typed. A page a click carried to the other session stays the page's choice too. Without your click a page can't make Tavora load an address for it, which the site would take for one you typed (its SameSite=Strict cookies go along and `Sec-Fetch-Site` says `none`).
- Only `http` and `https` pages open. `file:`, `tavora-module:` and other app protocols are refused, including through redirects.
- No new windows open. A clicked link that asks for one opens as one new tab, with the referrer the page would have sent.
- Downloads never write a file. Permissions are denied, except writing to the clipboard and fullscreen inside the panel. No device pairs over Bluetooth.
- A public page cannot reach the user's PC or local network: requests to loopback, private and link-local addresses, local name endings and common router names are cancelled. This holds from the moment the panel starts going to a public page, also when it leaves a local one, not only once the page has loaded.
- Bad certificates are refused, with no way to click through. The address field shows the address as Chromium reports it, so a name with letters outside ASCII shows as punycode (`xn--…`); hovering it shows the name, readable for Latin letters and still as punycode for any other script, so `аpple.com` (Cyrillic а) can't pass for `apple.com`.
- A site that asks for a client certificate gets none, so no page learns who you are from one.
- Ads and trackers are blocked in the main process, with EasyList and EasyPrivacy rules. No script is added to pages. Tavora calls into a page only for `document.exitFullscreen()` when you leave fullscreen with Esc or the toolbar, and to [fit a panel](#how-a-module-runs) when you double-click the line next to it.

## Accounts and modules

Tavora accounts are optional. Modules learn nothing about them: no SDK call, bridge message or module view carries the user's email address, the sign-in, an account id or anything made from one. The one exception is a module granted the `leaderboards` connector: it learns whether the user is signed in, and, once the user agreed to show their results there, the name its boards show for them (see [Leaderboards](#leaderboards)). How accounts handle data is on the [privacy page](https://mytavora.app/privacy/).

The maintainer can read Tavora's own conversations and reported conversations, and nothing else you wrote to a developer. The maintainer can see the list of accounts and every detail the service keeps about each one (email address, Discord name, profile, devices, developer name, keys, publish tokens' names and dates, modules, reviews, the size and date of a cloud copy), on the private admin page that only the maintainer reaches. Never a secret: the service doesn't keep your sign-in or publish token itself, only a hash, and the page never shows even that. The maintainer can **suspend** an account, for example after abuse: it is signed out on every device, can't sign in or publish, its reviews are hidden, nobody can start a new conversation with it, its leaderboard results are left out, and it gets an email with the reason. Lifting the suspension undoes exactly that. A suspension can be lifted, and then you sign in again. Replies a suspended developer wrote under other users' reviews stay visible. The maintainer can't read your cloud copy, and deleting an account stays yours alone: even while suspended, you can have it deleted by proving it is yours with a code to its address or a fresh Discord sign-in, without getting a sign-in.

A sign-in alone can't take an account away from you:

- **Changing the email needs both addresses.** Tavora sends a code to the new address and one to the current address, and both must be typed in. An account without an address confirms with a fresh Discord sign-in with its own login instead. Once it's changed, every other device is signed out, codes still waiting for the old address stop working, and the old address gets a note.
- **The other changes need the mailbox too.** Removing the email, connecting or disconnecting Discord and deleting the account each need a code sent to the account's address (an account without one deletes itself with a fresh Discord sign-in). Every device is listed under Account and can be signed out from another.

A developer can link a publisher key to their account, so users see a developer name instead of the key's fingerprint:

- **Only whoever holds the key can link it.** The signed-in app gets a one-time code (10 minutes, used once); the key signs it (Tavora itself for a key it keeps, `tavora-pack link` for a key file in CI), and the service checks that signature against the public half it was sent. The secret key never leaves the developer's PC, and the service keeps only public halves.
- **A name cannot pose as another.** Developer names are plain letters, digits, spaces, dots, dashes and underscores, unique when case and those separators are ignored, never Tavora's, changeable once every 30 days, and a name given up stays blocked for others for 30 days.
- **Users learn a name, nothing else.** Tavora asks the service which name a key has (only while online features are on, at most once a day per key) and gets the name alone, never an account or an address. The name shown is a label: what a user installs is still decided by the key's signature, as before.

### Publisher keys Tavora keeps

Tavora keeps a developer's publisher keys (Settings > Developer > Publishing), so the recovery key is the only thing they have to keep safe.

- **They are sealed with your recovery key.** The keys sit in your account's vault, sealed on your PC with a key derived from the recovery key, so the service only ever sees sealed bytes. Each PC keeps the vault as it last read it, sealed the same way, so signing works offline. It keeps only a vault its key opens.
- **They stay with your account.** The key and the vault a PC keeps are noted as your account's, and each account signed in on a PC keeps its own. When the service ends a sign-in by itself (signed out from another device, or unused for a long time), yours wait on the PC for you: another account signed in there later never sees, exports, sends or uploads them, and its own key never replaces yours. Sign out removes only your own key and vault from that PC. An older Tavora on the same PC (after a downgrade) reads only the key of the cloud copy (`account-key.json`), not the keys kept for other accounts.
- **The service can't make a PC drop them.** When the service sends a vault this PC's key doesn't open, the PC keeps its key and the vault it last read, goes on using those, and says so in Recovery key, where the new recovery key can be typed in, or got from another PC, if you made one there. Such a PC never hands its old key to another PC, and checks that its key still opens the vault before it sends it. When the vault is missing, and still missing when a PC looks again a few seconds later, it puts back the one it last read. A vault a PC has seen is never replaced by an empty one unless you confirm it there.
- **Only Tavora's own buttons sign.** Tavora signs when you press Publish on the review screen, or Save as zip in Settings > Developer or a module's menu, and at no other time. It opens no pipe, socket or port for signing, so no other program, web page or module can ask it to sign.
- **What you see is what gets signed.** Tavora packs the zip itself from your module's project folder and shows the review screen from that zip: its name, version, patch notes and what it asks for. Pressing Publish there signs and uploads that zip and nothing else; the press is your yes.
- **A key leaves Tavora only when you export it**, to a file you pick, to publish from CI (Settings > Developer > Publishing > Publisher keys and CI). Packing works with that file alone; publishing also needs a publish token.
- **A private key never goes out in a module.** Tavora's Publish and Save as zip and `tavora-pack` take the manifest, the folders of the entry pages, the icons, screenshots, readme and changelog; when an entry page sits next to the manifest, the whole folder except dot files and `node_modules`. They stop, naming the file, when that would take a key file (`.pem`, `.key`, `.p12`, `.pfx`, `.ppk`, in any case), the `--key` file itself, or a file holding a PEM, OpenSSH, PGP or PuTTY private key. The catalog refuses a zip that holds one too, so one packed by an older `tavora-pack` isn't published.

### Publishing to the catalog

- **The key alone publishes nothing.** Every upload carries the key's signature over the zip's SHA-256 and a sign-in of the account the key is linked to: Tavora's own, when you press Publish, or a publish token, from CI. An upload with only a key, or with the sign-in of another account, is refused.
- **Publish tokens are narrow.** A token is shown once and the service keeps only its hash. It works for a year, is removed in Settings > Developer > Publishing > Publisher keys and CI, and publishes only under id prefixes the account already holds, so it can't claim a new one. It can also list the account's versions still waiting for review and take one back (`tavora-pack withdraw`), and nothing else: it can't sign in, read the account or change anything else.
- **Every upload and withdraw is told.** The account's email address gets a mail for each published version, naming the module, the key and whether it came from Tavora or which token, and one for each version taken back from review, naming the module and whether it came from Tavora or which token.

## Leaderboards

A module granted the `leaderboards` connector can keep leaderboards (the boards its [manifest](../reference/manifest.md#leaderboards) declares) on Tavora's service, under the user's Tavora account.

- **Tavora asks first, in the panel.** Before a module's results go public, `leaderboards.show` (only right after a click in the panel) shows Tavora's own question in that panel's place, while the module's page is hidden and paused: "Your Tavora name and your results in this module will be public", with the name the boards will show. The module can't draw, answer or skip it. Signed out, the question offers to sign in instead. Nothing is sent before the user says yes.
- **The sign-in stays in Tavora.** The main process talks to the service; the module gets names, ranks and numbers, never a token, an account id or anything made from one. A board line marks only the user's own one (`self`). The module learns the user's name only once it is public on its boards.
- **Names are the users' Tavora profile names, checked.** A name the word filter refuses (the one for reviews), a name the maintainer hid, or no name at all shows as a neutral name such as "User · K7", made for that user and module; the account keeps its name. Suspended and banned accounts are left off every board.
- **Switching it off deletes.** `leaderboards.hide` (only right after a click) takes the user off that module's boards, and the service deletes their results for it. The user can do the same with Leave in Settings > Connections > Leaderboards, whatever the module offers, also after taking the grant back. Deleting the account deletes them everywhere.
- **The maintainer allows each catalog module.** A catalog module's boards run only once the maintainer allows that module, and they are the boards its newest listed version declares, so a copy can't make up new ones. Any copy not installed from the catalog (a development folder, or a zip signed with any key) gets test boards on the service instead, under `local.` and its id, whatever id or key it has; only its developer sees them, and an account keeps at most 10 of them.
- **A user's own ranks stay theirs.** `leaderboards.mine` gives a module only the user's own standing on its own boards, the same numbers its boards show anyway. Tavora's profile card lists the user's ranks on every catalog module they agreed to be shown in; only Tavora reads them, with the user's sign-in, and the user can hide that list. There are no public profile pages.
- **It's a casual ranking, not a verified one.** Results come from the user's PC, so a determined user can fake their own. The service checks every result on its own: a well-formed id, a time at most 5 minutes ahead and a year back, one result per day on a daily board, and every result only within its day (so an archive replay never counts, and an old game can't land in a past week or month). It also limits requests per account and module, results per request (50) and results kept per account and module (10,000).

## What Tavora counts

Tavora counts a few things as plain daily totals (per UTC day) so the maintainer can see how the project is used. A count is a number that goes up by one. Nothing about who is kept: no address, no id of a PC or a user, no request log, and a user without an account is never counted as a person.

- **App downloads.** How often each installer version is downloaded from the update feed. The feed's web server tells the service the file name when a download starts and nothing else, and the service keeps the version and a number. The installers on GitHub's release pages are counted from GitHub's own download numbers, which the service reads once an hour.
- **App updates.** How often each version finished downloading as an update. The app tells the service the version number, only while online features are on, with no cookies, referrer or sign-in. The app marks its own update requests with a header, so an update is never counted as an installer download.
- **Module installs and updates.** How often each catalog module was installed from Browse or updated. The app sends only the module id, as it already did for installs.
- **Website visits.** When mytavora.app opens, the page tells the service which site the visitor came from (only its domain, such as reddit.com, or nothing), and when a download, docs, GitHub or privacy link is clicked, which one. The service counts the visit by that domain and by country, which it looks up from the address in the free country database of [DB-IP](https://db-ip.com) (IP geolocation by DB-IP, CC BY 4.0) and then forgets. No cookie, no id and no address is kept, and programs that say they are bots are not counted.
- **Page statistics on the website and these docs.** mytavora.app and docs.mytavora.app also use [Umami](https://umami.is), self-hosted by the maintainer at stats.dkiessling.de, with no third party. It counts page views (which docs pages are read), the referring site, country, browser and operating system, and clicks on the main links on mytavora.app. No cookie and no personal data are kept, and the address is not stored. If your browser sends Do Not Track, Umami counts nothing (it does not check Global Privacy Control). This is separate from the totals above; the app itself sends nothing to it.
- **Accounts, once a day.** How many accounts exist and how many used a sign-in in the last 7 and 30 days, as three numbers. Nobody is named.

The numbers are shown on the private admin page, which only the maintainer reaches. Anyone can send the counting calls, so the totals are a guide, not an audit.

## The cloud copy

The cloud copy (Profile > Cloud copy) keeps your Tavora data on Tavora's service or in a folder you pick, so your other PCs get it. It is optional and off until you turn it on.

- **Only you can read it.** It is encrypted on your PC with AES-256-GCM, under a random key made there. The key leaves your PC only as the recovery key Tavora shows you. The service keeps sealed parts, a sealed list of files and a version number; parts are named by a keyed hash, so their names say nothing without the key. The key is kept with your system's key store, and the copy can't be turned on where there is none.
- **One key for the account.** The key belongs to your account, not to one PC: the first PC that needs it makes it, and the others get it from one of your PCs ([below](#adding-a-pc-from-another-one)) or ask for your recovery key. A small vault sealed with a key derived from it (at most 64 KB, holding the publisher keys Tavora keeps) stays on the service and goes out only to a signed-in PC of the account; that it exists tells a new PC to ask for your key instead of making another. Signing out forgets your key on that PC (only yours); turning the copy off doesn't. A key a PC keeps is used only for the account it belongs to: while another account is signed in, your copy stays off, and it goes on when you are back, unless that account turned a copy of its own on meanwhile (then yours is off until you turn it on again).
- **A lost key starts over, never overwrites.** Start over makes a new key and replaces the copy with this PC's data under it. The publisher keys in the vault are lost with the old key; a key linked to the account can be replaced as [A lost or leaked key](./publishing.md#a-lost-or-leaked-key) says. A PC with the old key can't open the new copy, so it stops syncing and asks for the new key; it never writes over the copy, and it keeps its old key and the publisher keys it last read until the new key is typed in.
- **Room is shared fairly.** So no one fills the service for everyone, it also keeps when your account was made and a keyed hash of the network you last added to it from (the first three parts of an IPv4 address, the first three groups of an IPv6 one), under a secret kept on the server, never the address itself. Accounts of one network hold at most a tenth of the service's room together (the maintainer can change that share).
- **It holds your Tavora data and nothing else.** That is what the daily backup holds (library, layouts, profile, every module's data, pictures), plus the installed modules and who publishes them. Sign-ins (Tavora's, Discord's, AI usage accounts), grants and Browser panel data are never in it.
- **A copy is checked before it is used.** Every part must open with the key and match its name, and every file its size and SHA-256. Every path must be one of the copy's own places: no `..`, absolute paths or other folders, and in the module files folder only Tavora's own folders. A copy is downloaded into a staging folder and swapped in only at start, before anything reads the data; what was there moves to the backups folder.
- **Modules in a copy come from you.** Only your key can make a copy, so its modules are not checked again like a new install. The safety lists still apply at start, and grants are not copied: a module asks again on each PC.
- **Older data never replaces newer.** The service takes a new version only from a PC that started from the current one. Otherwise you choose which side to keep, and the other is kept as a local backup. Each sealed list also names the version it was saved on top of, so even a broken-into service can't slip a PC an older list as a newer version: a list saved on top of a version older than the one the PC last synced is never taken on its own, and you choose which side to keep (that also happens after a copy was deleted and made again). Lists saved by an older Tavora have no such mark and are still read, until a PC has seen one that has it: from then on, that PC treats a list without the mark as an older one, and you choose.
- **A folder holds the same sealed copy.** In a folder you pick (usually one OneDrive, Dropbox or Google Drive syncs), Tavora writes only the sealed parts and lists, in a `Tavora` folder inside it, and your sync app moves them. Tavora's service is not used, and no account is needed: signed out, the key stays on your PC, kept like the account's key, and signing out doesn't turn a folder's copy off: your key stays for it, only the saved vault of publisher keys goes from the PC. Signed out, Show key (and adding a PC through the folder) gives an account's key only while a copy in a folder is on with it, and a key made signed out (one of no account) as it is; a copy turned on signed out gets a new key of its own, never the key of an account that was signed in before. Anything in that folder is checked like a download, since other apps and PCs can write there. Tavora only reads the names it writes, seals each list's version inside it so an old list can't pose as a newer one, never takes a list older than the one it last synced, and asks you which side to keep when two PCs saved at once. Deleting the copy removes only Tavora's files.
- **Modules and pages can't reach it.** No SDK call, bridge message or module view carries the copy, its key, the vault or whether it is on.

## Adding a PC from another one

A new PC can get the account's key from a PC that has it, so you only type the recovery key when every PC is gone. It is the same key, so the new PC can open the cloud copy and the publisher keys Tavora keeps.

- **Nothing on the way opens the key.** The new PC makes a one-time X25519 key and asks; an old PC answers with its own one-time key. On your click, the old PC seals the key with AES-256-GCM under a key both PCs derive from the two one-time keys, and only the new PC can open it.
- **Signed in, Tavora's service only passes it on.** It holds the request in memory, for 10 minutes and one per account, between PCs signed in to the account; the sealed key goes to the new PC once and is gone. Signed out, with the cloud copy in a folder of your own, the same steps go through files in its `Tavora/pairing` folder instead. Such a request lasts 24 hours, since a sync app can be slow, and Tavora reads only the names it writes there.
- **Nothing goes or is kept without a click on both PCs.** The old PC shows "Add *PC name*?" with a 6-character code, and the new PC shows the same code. The old PC sends the key only on Add, and the new PC keeps it only after you click Codes match there; a key that comes first waits, unopened. The code comes from both one-time keys, and the new PC commits to its key before it sees the old PC's, so no one in between (the service, or anyone who can write the folder) can swap a key or plant one of their own and still get matching codes.
- **A stolen email account isn't enough.** Someone who signs in with it can ask, but gets the key only if you click Add on one of your PCs. Only add a PC you are setting up yourself, and only when the codes match. If you didn't ask, click Not me and sign that PC out under Account.
- **Modules and pages can't reach it.** Requests and answers stay in Tavora's main process, like the key itself.

## Revoked keys, blocked modules and lost keys

Tavora keeps three lists for modules from other people: publisher keys that were revoked, module zips it blocked, and new keys that replace an account's lost one. They are signed with Tavora's catalogue key, which is kept offline and never on the service.

- **Only Tavora's signature counts.** The app checks every list against the catalogue key built into it. A list signed by any other key, or older than the one the app already has, is ignored, so a service that was broken into can hold a new list back but cannot lift a block or revoke a key. Before signing, Tavora's signing tool shows every entry a new list adds, drops or changes against the list in force, and drops or changes one only when the person signing names it, so a list the service prepared can't slip a change past them.
- **The lists come only while online features are on**, from the Tavora service, like hosted game icons: no cookies, no referrer and nothing that says who asks. The app never sends which modules it has.
- **A revoked key installs nothing new.** A zip signed by it is refused, for a first install and for an update, unless Tavora listed that exact zip as signed before the revocation. A module already installed keeps running.
- **A blocked zip stops at once.** Its panels close, it does not load, and Settings > Modules says why. Its data is kept, and it comes back only with a zip that is not blocked. A block names the zip's SHA-256 or the SHA-256 of what its signature covers (the publisher key and every file's hash), so the same signed files packed again, recompressed or with a zip comment added, stay blocked. Tavora blocks a zip from the catalog by both, so versions of the app from before this still match the first. For an old version whose zip the catalog no longer keeps, only its SHA-256 is known.
- **A new key replaces a lost one only by a signed statement.** Updates signed by the new key are accepted for the old key's modules, and their data stays where it was. Without a statement, a zip from another key is another publisher, as before.
- **Asking for one changes nothing by itself.** "Lost it?" in Settings > Developer > Publishing only queues a request on the service: both keys must be linked to the signed-in account, and the account's email address is told. A person at Tavora checks it, exports the waiting requests and signs them offline with the catalogue key, so a stolen sign-in or a service that was broken into still can't move a module to another key. The one thing a request does at once is stop the catalog from taking new uploads signed by a key reported as leaked, and from approving ones that were still waiting for review. That stays when the account unlinks the key or is deleted: no account can link it, and its revocation still gets signed. A key the signed lists revoke can't be linked either.

## Tavora's own updates

Tavora updates itself from `updates.mytavora.app`. That server alone is not trusted to say what gets installed.

- **Only Tavora's signature counts.** Each release is signed offline, on the maintainer's PC, with Tavora's update key: the signature covers the version, the installer's file name and the installer's SHA-512, and travels in the feed's `latest.yml`. The app installs a downloaded update only when the signature holds for the version it is about to install, the name of the file it saved and the SHA-512 of the bytes in that file (worked out from the file, never read from the feed), under one of the two keys built into it: the release key, or a backup key kept apart for when that one is lost. The private keys never go to CI, the repository, the server or a log.
- **Nothing else installs.** A missing, broken or foreign signature, a changed installer, a relabelled version, or a version not newer than the running one is refused: the downloaded file is deleted, the update marker and Settings > About say the update was skipped, the reason goes to the update log (in Copy diagnostic info), and Tavora goes on with its version and keeps checking. Neither Restart now nor quitting installs anything that wasn't checked: the updater's own install-on-quit is off, and Tavora installs only a version that passed. A feed that asks to run the installer with admin rights or to fetch an extra package is refused too, since the signature doesn't cover those.
- **Signed only after the build is checked.** GitHub Actions builds and tests the installer with no secrets at all; the maintainer's PC signs only files whose SHA-256 and GitHub build attestation match that build, from that commit on `main`. The installer and its blockmap stay exactly as attested; `latest.yml` gains the signature line after that check, so the published `latest.yml` no longer matches its attestation, by design.
- **The feed takes only signed updates.** Before it publishes a release, the server that receives the upload checks the same signature, for that version, file name and installer, against the two keys the app pins (installed there by the maintainer, never by an upload). It also takes `latest.yml` only exactly as the release build writes it for that one installer: one file entry, no web address outside the release notes (which are plain text there and can't add a field), nothing that asks for admin rights or an extra package, since the signature doesn't cover those. An upload that fails either check never goes on the feed, so a stolen upload key can't put an installer there that Tavora's key didn't sign, not even for versions from before signed updates.
- **A server that was broken into can at most hold updates back.** It can't make Tavora install another installer, a version older than the one it runs, or a release under another version number. It can still offer an older signed release (newer than yours) instead of the newest one.
- **Proven end to end.** Every release build installs the version it builds, offers it a test build of the next one from a local feed and checks, with the real updater and throwaway keys, that unsigned, foreign-key, changed and relabelled updates are refused and that updates signed by either pinned key are taken and install on quit (`apps/desktop/scripts/update-check.mjs`).

## Themes and styles

Themes (`tavora.theme.json`) and design styles (`tavora.style.json`) are data only, checked against a strict schema before they load: colours, picks from a fixed list of looks, and numbers kept in their ranges. Tavora reads nothing else from their folders, so a theme or style can't run code, add CSS, load a font or a file, or reach a module; a style picks only fonts Tavora ships. Ids starting with `tavora.` load only from Tavora's own folders. The user's own come from their data folder, which only the user (or someone who can already act as them) can write.

## Known limits

- **The sandbox is Chromium's.** A Chromium renderer exploit would break the isolation guarantees, so Tavora follows Electron releases. Electron fuses turn off `RunAsNode`, `NODE_OPTIONS`, `--inspect` and extra `file://` privileges, keep cookies encrypted, and load the app only from its `app.asar`, which must match the hash built into `Tavora.exe` (CI reads the fuses of the packaged build in every check run and every release build). A few files sit next to the archive, outside that check: the system-info worker and the `koffi` library (with its native file) that it and the main process load to call Windows. A packaged Tavora quits when started with switches that weaken the sandbox or the network rules.
- **Someone who can edit Tavora's files** on the PC can already act as the user. Local files are not protected from them.
- **CPU and memory are not capped.** A busy module is shown as not responding and can be stopped, but it can still use whatever its renderer gets.
- **Panels of one module share a process.** Several panels of the same module in one workspace share a renderer, so a crash can take down its siblings, but no other module.
- **Side channels** such as DNS prefetch or timing between modules are not fully addressed.
- **A stream overlay page in OBS can use WebRTC.** Its policy and its frame keep it from loading from, connecting to or navigating to any other address, but OBS's browser doesn't let Tavora turn WebRTC off. A module with stream overlays could send what it published for the page off the PC that way, even without a website grant.
- **The Browser panel has no Safe Browsing.** A phishing page still renders. A public name that resolves to a local address (DNS rebinding) is not caught there, because the panel checks names, not resolved addresses. Sign-in popups that need `window.opener` do not work.
- **A click lets a Browser page have one address loaded by Tavora.** A link opened in a new tab, or one that takes the panel to the other session right after a click or key press, is loaded by Tavora itself, and so are the redirects of that load. Apart from the referrer the site gets it like an address you typed: its SameSite=Strict cookies go along and `Sec-Fetch-Site` says `none`. One click allows one such load. The page the panel reopens (the one it showed last time), Reload, Back, Forward and Try again are loaded the same way, also when the page went to that address by itself; only a move to the other session asks.
- **Discord's pipe isn't checked on Windows.** While the Discord connector is paused, Tavora doesn't open the pipe. Whatever listens where the Discord app listens gets the Discord token. On Windows that is a named pipe, and another account on the same PC could claim Discord's pipe name first and catch the token. Any program running as the user is trusted too.
- **Users who stay offline, or turn online features off, do not get new safety lists.** A revoked key or a blocked zip still works for them until they go online, and an unsigned module that is already installed is not stopped by a block.
- **The first install trusts HTTPS alone.** Tavora's installer has no Windows code signature (Authenticode) yet, so Windows warns when it is first run, and an installer downloaded from the website is checked by nothing but the HTTPS connection. Tavora's own signature covers updates, from the first version that checks it on.
- **Versions from before signed updates trust the feed.** They install the next update on the feed's word; from that version on, every update is checked. The feed publishes only signed uploads, but someone who broke into the server itself, past the upload, could still offer those versions another installer.
- **A leaked update key works until apps move past it.** Installed apps trust both pinned keys until they install a release that pins a new pair, which the other key has to sign. Between the check and the install, the downloaded installer sits in the user's own cache folder, where someone who can edit the user's files could swap it (see above).
- **Unsigned local modules are known only by their id.** Another local module put in the same folder under the same id gets its grants.
- **A development folder is a module's whole bundle.** A module loaded from a development folder (Settings > Developer > Project folders) can read every file in its project folder, such as its sources or a `.env` file, because G6 is measured from that folder. It is an unsigned local module, known only by its id. Add only your own projects.
- **A downloaded built-in module is checked when Tavora starts or looks at its modules, not on every file read.** Someone who can edit files in Tavora's data folder while it runs could still change a file after the check. They can already act as the user (see above); the next start checks the folder again and falls back to the shipped copy.
- **WebAssembly is allowed only for Tavora's own modules** that ask for it, because the Whiteboard needs it. Community modules do not get it.
- **A panel running with its game shares its data with the module's other panels in that workspace.** It runs in the same session, so the same storage, documents and files, as a panel of that module the user sees there. That is by design (it records what the open panel shows), but a page of the module can't be kept from reading what another page of the same module wrote.

## Shared item tooltips

`ui.tooltip` renders checked, bounded plain content above neighbouring panels in a
separate host-owned surface. It accepts text, semantic item colours (in the `poe` look), badges,
requirements and modifier rows, plus a raster asset inside the calling module's
bundle. The look is the host's own: neutral in Tavora's theme colours, or the fixed `poe` look a module can pick
by name. No HTML, module styles, links, scripts, remote images or arbitrary file
paths are accepted. Image reads stay inside that bundle and are limited to 512 KB. An item card's stats may each name
a small icon by the same path rules (PNG or WebP only), read the same way and limited to 64 KB; the page shows it only as a mask in the
label's colour, and only as a `data:` URL it checks again.

An item card may wear a skin the module defined (`ui.tooltip.defineSkin`). That is the one way a module's own colours,
a frame picture and a font reach the host's tooltip window, and each is a checked value, never CSS: colours must be
`#rrggbb` and readable (contrast 4.5:1 for text, 3:1 for the accent line on the surface and for the effect box's edge),
or the skin is refused. The frame picture and the
font are read only from the module's own bundle under `dist/`, by the same path rules as the item picture (no `..`,
no link or junction out of the bundle), and must be a PNG or WebP picture or a WOFF2 font by their first bytes, up to
512 KB each (checked on the open file; the read stops one byte past the limit).
Tavora inlines them as `data:` URLs; the window's content policy gains only `font-src data:`, so nothing is loaded from
anywhere else. The font is used for the card's title and effect box only (on a unit card, for the whole card but its
footer), and Tavora sets every size. At most 32 skins
per module and 16 MB of skin files for all modules together are kept, in memory, until the module reloads, updates, is
turned off or removed.
The surface has its own sandboxed renderer and session, no administrative host
bridge, and no permissions. Its footer identifies the source module.

Hover requires recent trusted pointer or keyboard input in a visible source panel: the pointer the panel's preload
reports must be near the card's anchor point, or over the anchor's box when the module sends one (at most 600 px a side,
with the point on it). The box only widens where in its own panel a module's hover is taken: the card may then open up
to 600 px from the pointer, still anchored inside that panel.
The card is placed beside the module's box (or the point it gave) and is a window of its own, so it can reach outside the
panel it belongs to, over a neighbouring panel or the edge of Tavora's window; it never leaves Tavora's content bounds.
Where nothing fits, or the module gives no box, it may cover the item it is for.
Hover details pass mouse input through and do not freeze the workspace. Pinning
requires a real click or key press, once per gesture. One tooltip is shared by the
window; ordinary hover cannot replace a pin. Only the owning panel can move or
close its current tooltip by id. Escape and the host close button always dismiss
it. Source hide, reload, close, workspace switch, app focus loss and host dialogs clear
it; stale asynchronous requests cannot revive a closed tooltip. Tooltips stay
inside Tavora's content bounds and do not open remote pages.

## Crash log

When the GPU process, a helper or a page (Tavora's own or a module's) goes away unasked, Tavora adds one line to
`logs/crashes.log` in its data folder (the newest 100 are kept). A line holds what went, why, its exit code and, for a
module's page, the module's id, so it says which modules you run. It stays on this PC and is never sent anywhere.

## Isolated public page importing

`network.readPage` renders one public HTTPS address in a hidden, sandboxed browser,
using a new temporary session for every call. It shares no cookies, storage,
sign-ins, client certificates, browser tabs or bridge with the user or the module. The module supplies
only a URL; it cannot inject JavaScript, click, fill forms, choose headers or read
cookies. Tavora returns bounded page HTML, title, final URL and status after loading.
It reads them in a script world of its own, which the page's scripts can't change,
and passes on only those, checked again for type and size.
The page's own scripts may run, without Node or a preload. Popups, webviews,
downloads, device access and permission requests are refused. Login and verification
pages fail instead of asking for interaction.

Every page, script and data request needs an exact granted domain and HTTPS on the
standard port. Only GET/HEAD document, script, stylesheet and XHR requests are allowed;
images, media, fonts, frames, sockets and other resource types are blocked. A mandatory
session proxy resolves each connection, refuses any non-public address and connects
to the checked IP, so a second DNS resolution cannot redirect it into the local network.
Chromium still checks the destination's TLS certificate. Non-proxied WebRTC UDP is
disabled. This session never uses the user's Browser session or system proxy.

One import per module may run at once, for at most 30 seconds, with 200 resource
requests, 100 connections, five redirects, 20 MiB of total tunnel traffic and 5 MiB
of returned HTML. The window, tunnels and temporary storage are cleared after each
call; closing, reloading or disconnecting the source panel cancels its import.
An import can fail when a site needs resources on domains that were not granted,
requires interaction or changes its page format. No protection or verification is bypassed.

## JSON file exports

`files.exportJson` is the older way and stays for modules made before `files.saveJson`; new modules use `files.saveJson`. Both save the same way: after a real module click or key press, consumed once per request, and not from a panel over the game, Tavora's save dialog opens with the suggested name filled in, in the folder where you last saved or opened a file of that module (at first Documents\Tavora). Nothing is written until you pick the place; closing the dialog writes nothing and shows no message. At most 8 MiB of valid UTF-8 JSON is accepted, and the host serializes it itself. Suggested names are sanitized, paths and extensions cannot be supplied, and replacing a file needs your OK in the dialog. Modules receive only the resulting file name, never a filesystem path. Saving does not grant arbitrary filesystem access. (Older Tavora versions wrote `files.exportJson` files into Downloads\Tavora without asking.)
