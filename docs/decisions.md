# Decision log

The installer, updater, feed, release-channel and signing decisions below describe the release process. Implemented: the Windows NSIS installer, automatic updates and `pnpm release` (0.3.1 to 0.3.3), publishing to `updates.mytavora.app`. Not implemented: the beta channel, signing and Linux (AppImage) updates. The existing `pnpm dev` Vite hot reload workflow supersedes the earlier rebuild-only proposal from PR #6.

2026-10-14 developer docs live in this repo as `apps/docs` (VitePress); the marketing site stays in `tavora-website`. Manifest, protocol and SDK docs change alongside code; TypeDoc generates the API reference and the manifest schema is published with the built site. The site is published at docs.mytavora.app as static files behind Caddy on the existing Hetzner server, like mytavora.app, rather than GitHub Pages: the server already hosts the other apps, and no deploy key has to live in GitHub. `apps/docs/scripts/Deploy-Docs.ps1` builds on the PC and switches to a new release with rollback; publishing is manual.

2026-10-14 merge validation: startup removes expired-game browser partitions before opening Chromium sessions, avoiding Windows file locks. The SDK remembers current suspension and informs late suspend subscribers, so a panel hidden while connecting still pauses its work. Existing expiry and docking gate tests cover both behaviors; the SDK has a late-subscription regression test.

2026-10-14 integration: standalone test packages use electron-builder (Windows portable exe/zip and Linux AppImage), include official and example modules in separate resource folders, and remain unsigned. Native title bars and menus are replaced by system window controls over Tavora's draggable header; interactive header controls opt out of dragging. The game rail uses the pill and hover treatment requested in PR #4; this is a specific exception to the original general hover rules.

| 2026-10-16 | Module data belongs to a publisher, not to an id (finding S5; Nik's answers in a grilling). (1) The publisher is a signing key: the SDK's pack command makes an Ed25519 key pair on the developer's PC the first time and reuses it, and signs the zip (the manifest and a hash of every file). The secret half never leaves the developer's PC; Tavora's server never holds one. Module data, settings and web storage are keyed by owner and id (`module-data/<owner>/<id>/<game>`, partition `persist:module:<owner>/<id>@<game>`), where the owner is `official` (Tavora's own folder, as today), `local` (any unsigned folder module, which keeps working with no key) or the fingerprint of the publisher's first key (rule 4 keeps it through key changes); existing data moves to `official` or `local` once on first start. The installer checks the signature before extracting and records the owner in the host's own list, never in the module's folder. An installed module updates only from a zip signed by the same owner. (2) A module whose owner differs from the one that left data under its id starts empty; the old data stays set aside, comes back if that owner's module returns, and can be deleted in Settings > Modules. No prompt at install hands data over. (3) The one exception is the player's own testing: a signed module whose id has `local` data offers "Move data from the local copy" in Settings > Modules, only on a deliberate click there. (4) With accounts (Foundation 1 step 6) a developer adds the public half of their keys to their profile, so the catalogue shows a name instead of a fingerprint. An account can reclaim its work after losing a key: it registers a new key, the catalogue issues a statement signed by Tavora's catalogue key that the new key succeeds the old one, and the app moves the data across without asking. Without an account a lost key means a new author (rule 2); only keys linked to an account before the loss can be reclaimed. An account can also revoke a leaked key (Nik's addition): the same succession moves its work to a new key, and the old key goes on a revocation list the service publishes, signed by Tavora's catalogue key. The catalogue refuses uploads signed by a revoked key and tells the account owner when one is tried. A signature does not show when it was made, so the catalogue keeps the hash of every package it accepted under the old key before the revocation; those stay valid, and any other package signed by the revoked key is refused. The app fetches the list while online features are on, refuses to install or update from a revoked key (except a listed hash) and says why; modules already installed keep running and take their next update from the new key. The owner in the data path is the owner's first key fingerprint and stays the same through every succession, so players keep their data with no move step. Where the app refuses such a zip, the player can press Report, which sends only the module id, the key's fingerprint and the zip's hash (nothing about the player) so the owner is told; nothing is sent without that press. (5) The catalogue reserves an id prefix per account, first come (`tavora` stays Tavora's), and accepts `<prefix>.*` modules only when signed by that account's keys.
