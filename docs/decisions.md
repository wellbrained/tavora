# Decision log

The installer, updater, feed, release-channel and signing decisions below describe the planned release process. Current test packaging remains portable exe/zip and AppImage; automatic updates, NSIS installers and the feed are not implemented yet. The existing `pnpm dev` Vite hot reload workflow supersedes the earlier rebuild-only proposal from PR #6.

2026-10-14 developer docs live in this repo as `apps/docs` (VitePress); the marketing site stays in `tavora-website`. Manifest, protocol and SDK docs change alongside code; TypeDoc generates the API reference and the manifest schema is published with the built site. The site is published at docs.mytavora.app as static files behind Caddy on the existing Hetzner server, like mytavora.app, rather than GitHub Pages: the server already hosts the other apps, and no deploy key has to live in GitHub. `apps/docs/scripts/Deploy-Docs.ps1` builds on the PC and switches to a new release with rollback; publishing is manual.

2026-10-14 merge validation: startup removes expired-game browser partitions before opening Chromium sessions, avoiding Windows file locks. The SDK remembers current suspension and informs late suspend subscribers, so a panel hidden while connecting still pauses its work. Existing expiry and docking gate tests cover both behaviors; the SDK has a late-subscription regression test.

2026-10-14 integration: standalone test packages use electron-builder (Windows portable exe/zip and Linux AppImage), include official and example modules in separate resource folders, and remain unsigned. Native title bars and menus are replaced by system window controls over Tavora's draggable header; interactive header controls opt out of dragging. The game rail uses the pill and hover treatment requested in PR #4; this is a specific exception to the original general hover rules.

| 2026-10-15 | Online game database: a Tavora service on Hetzner (`api.mytavora.app`, the first piece of `apps/api`) serves search from its own dataset. The app never calls a third party and holds no keys | No keys in builds, one place for source terms and rate limits, and it grows into the Milestone E catalog server |
| 2026-10-15 | Dataset: Wikidata (CC0) plus Steam's public app list (`IStoreService/GetAppList`, games only), rebuilt by a script and loaded by the service as a file. No IGDB | Wikidata has about 128,800 games with a Steam appid and needs no licence. IGDB's terms need a partnership for commercial use and say nothing on caching. Only about 7% of Wikidata games have aliases, so the aliases in `catalog.ts` stay |
| 2026-10-15 | A game has a canonical id, a name, aliases and an icon. The canonical id is Tavora's own name slug, issued once and frozen; existing ids stay as they are; a renamed game keeps its id and the old name becomes an alias. Steam appid and Wikidata item id are stored as hidden matching keys, never as the id | Players' data and a module's `games` list are keyed on the id. Names alone merge or duplicate games (remasters, editions), and keys let a dataset rebuild update a game without changing its id |
| 2026-10-15 | Search sends only the typed text, with no identifier, and the built-in list is the offline fallback. Settings has an off switch for online search. No local dataset sync in the first version | The app stays local-first and usable offline; the built-in list changes with app releases and online results come live |
| 2026-10-15 | Steam import: the player pastes a Steam profile URL or SteamID64, sees a preview, selects games and imports. The service holds one Steam Web API key, relays only `GetOwnedGames` and stores nothing about the library; it needs a privacy page and Valve attribution. Not gated on a Valve check | The library is the player's own, each call is user-initiated, and Tavora has no payment model. Valve's terms do not explicitly cover one shared key, so this is a known, accepted risk (100,000 calls per day; Valve may end access without notice) |
| 2026-10-15 | Import matching: a known appid maps to the database game; otherwise it becomes a custom game with a slug id and the appid is stored, never rewriting the id. An exact name or alias match with an existing entry counts as already owned and gets the appid attached; near matches are only flagged | No duplicates and no orphaned data |
| 2026-10-15 | Icons are Tavora's own: about 50 built-in games get icons drawn with PhotoCraft and VectorCraft as abstract themed symbols that never copy a game's logo, title lettering or characters, with a provenance file for prompts and settings. Every other game gets a deterministic generated badge, and players can still pick an image. Steam or Twitch icons may return later as optional extras | Steam and Twitch art is the publishers' work, and neither Valve's nor Twitch's terms settle storing it, so Tavora does not depend on it |
| 2026-10-15 | Build order: (1) the service, online search and the generated badge, (2) Steam import, (3) the drawn icon set | Step 1 has no outside dependency; steps 2 and 3 build on it |
| 2026-10-15 | The service is Node 22.18+ with Hono and `node:sqlite` (FTS5) over a read-only dataset file, bundled into one file with esbuild; no native dependencies and no `node_modules` on the server | The server already runs Node 22.23 with `node:sqlite`; one file and one dataset make a release easy to switch and roll back |
| 2026-10-15 | The dataset is built on a PC by `pnpm --filter @tavora/api dataset` and shipped with each release; the service never calls Wikidata or Steam while running. `apps/api/data/ids.tsv` records every id ever issued with its matching keys and is committed after each real build | Ids stay frozen across rebuilds and machines, and the service has nothing external to break |
| 2026-10-15 | Search API: `GET /v1/games/search?q=&limit=` returns `{ results: [{id, name}] }` (an object, so fields can be added later without breaking clients) ranked exact name, exact alias, name prefix, alias prefix, then every word as a word start; 60 requests a minute per client; never cached, no CORS, no request logging, and no access log in Caddy | Only what is needed to add a game leaves the service, and what a player typed is not kept |
| 2026-10-15 | The app trusts an online result only after strict validation (valid slug, capped name) and the main process makes the request, never a module or the page. `local-` is reserved for custom games: the dataset refuses it for canonical ids and the app refuses it from the service | Custom ids and canonical ids can never collide |
| 2026-10-15 | A custom game is merged with a database game by filling in its `catalogId`, never by renaming its id; an exact name or alias match links, near matches are only flagged, and a game already linked is shown as already in the library | The game's data is keyed on its id, and modules already match on `catalogId` too |
| 2026-10-15 | The generated badge keeps each game's existing tone and adds one of eight faint patterns chosen by a second hash of the id | Same id, same look on every PC, and no saved data changes |
| 2026-10-15 | Deployment: systemd unit `tavora-api` as its own user on 127.0.0.1:4010, releases in `/srv/tavora-api/releases` with a `current` link and rollback on a failed health check, Caddy site file `api.mytavora.app` imported by the main Caddyfile, scripts named `tavora-api-*.sh` | Mirrors the docs and website sites; the Caddy file has no access log and sets `X-Forwarded-For` itself |
